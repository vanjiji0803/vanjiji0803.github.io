把 Prompt 当成一段随手可改的字符串，是多数 LLM 应用上线后最先暴露的问题。它其实是一个**接口**：输入是结构化上下文（检索片段、工具返回、用户历史），输出是下游代码要解析的契约（JSON schema、函数调用参数、分类标签）。接口一改，调用方就得跟着改。所以它需要版本、测试和观测，和任何 API 一样。

## 版本：把模板和调用代码解耦

最朴素的做法是把模板硬编码在函数里，改一个字就要重新发版。更稳的是把模板抽成带版本号的资源，例如 `prompts/extract_invoice/v3.md`，配套一个 manifest：

```yaml
id: extract_invoice
version: 3
model: gpt-4o-mini
temperature: 0
output_schema: invoice_v2.json
changelog: 增加对多币种金额的约束
```

调用方只引用 `id` 和期望的 schema 版本，运行时由注册表解析到具体模板。这样 A/B 测试、灰度、回滚都变成配置操作。注意一个坑：模板版本和模型版本要**分别记录**。同一个 v3 模板在 `gpt-4o` 和 `gpt-4o-mini` 上表现可能差很多，回归基线必须绑定模型快照，否则你无法判断是模板退化还是模型漂移。

## 回归测试：别只看“感觉对了”

Prompt 回归的核心难点是输出非确定。我的做法是分层：

1. **结构断言**：输出能否被 schema 解析、必填字段是否齐全、枚举值是否越界。这类断言便宜且稳定，应该覆盖所有用例。
2. **语义断言**：对抽取类任务，用字段级精确匹配或归一化后的模糊匹配（金额去千分位、日期统一 ISO）。对生成类任务，用 LLM-as-judge 打分，但 judge 的 prompt 也要版本化，并且定期用人工标注的小样本校准 judge 的偏差。
3. **对抗用例**：空检索、超长上下文、注入式用户输入（“忽略以上指令”）、工具返回错误码。这些是线上事故的高发区，却常被 happy path 测试漏掉。

测试集不必大。我通常维护 30–80 条带标注的用例，按场景分组，每次模板变更跑全量，报告里给出**逐条 diff** 而不是一个总分。总分掩盖退化：可能修好了 3 条、弄坏了 2 条，平均分还涨了。

一个实际数字感受：抽取任务里，把 temperature 从 0.7 降到 0，结构断言通过率能从 82% 提到 97%，但语义字段的召回几乎不变——说明失败主要来自格式抖动而非理解错误。这类结论只有分层测试才看得出来。

## 可观测性：记录什么才有用

线上日志只记最终字符串是不够的。我至少记录：模板 id+version、模型名+快照、完整渲染后的 prompt（注意脱敏）、token 用量（prompt/completion 分开）、首 token 延迟与总延迟、解析是否成功、以及下游是否触发了重试或降级。

关键指标不是“平均延迟”，而是**解析失败率**和**重试率**。它们直接对应 prompt 契约的稳定性。另一个有用信号是 completion 的 token 分布：如果某天 P95 突然翻倍，往往是模型开始“自言自语”或模板里某段约束被稀释了。

追踪链路建议把 prompt 渲染作为 span，检索、工具调用、模型调用各占一个 span，这样一次请求里“是检索没召回还是模型没遵守指令”一目了然。采样上，成功请求低采样、失败和重试请求全量保留。

## 还没想清楚的问题

模板版本和 schema 版本的兼容矩阵怎么自动维护？我现在靠人工在 manifest 里写兼容范围，容易漏。另一个开放问题是：当 judge 模型本身升级时，历史回归基线是否要重跑？重跑成本不低，但不重跑就无法区分“模板退化”和“评委变严”。我倾向于对 judge 做固定快照并定期人工抽检，但还没在大规模流量下验证过。

把 prompt 当接口，短期看是多了版本和测试的负担，长期看是让“改一句话”这件事从赌博变成可回滚的工程操作。
