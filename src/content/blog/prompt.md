## 为什么Prompt是接口

很多人把Prompt当成一段自然语言字符串，改了就上线。但在生产系统里，Prompt是**模型与业务逻辑之间的契约**：它定义了输入变量的格式、输出结构的约束、以及模型行为的边界。一旦把它当作接口，版本管理、回归测试和可观测性就成了必需品，而不是可选项。

## 版本化：不只是git commit

最简单的做法是把Prompt模板放在代码库里，用git管理。但这不够。你需要：

1. **显式版本号**：在模板文件头部或元数据里标注 `version: 1.3.0`，遵循语义化版本。破坏性变更（如输出格式从JSON改为YAML）升主版本；新增可选变量升次版本；措辞微调升修订号。
2. **变量契约**：每个模板必须声明它期望的输入变量及其类型、是否可选、默认值。例如用JSON Schema描述：

```json
{
  "type": "object",
  "properties": {
    "user_query": {"type": "string", "maxLength": 2000},
    "context": {"type": "string", "maxLength": 8000},
    "language": {"type": "string", "enum": ["zh", "en"], "default": "zh"}
  },
  "required": ["user_query", "context"]
}
```

3. **渲染与校验分离**：用模板引擎（如Jinja2）渲染后，先校验输入变量是否满足契约，再调用模型。避免因变量缺失或超长导致模型行为漂移。

## 回归测试：用数据集锁定行为

Prompt的回归测试不是断言输出完全相等，而是验证**关键属性**。我通常分三层：

- **结构测试**：输出是否符合预期的JSON Schema。用 `jsonschema` 库校验，失败即阻断。
- **语义测试**：针对每个测试用例，定义必须包含/排除的关键词或正则。例如医疗问答中，输出必须包含“建议就医”且不得出现具体剂量。
- **模型评分**：用另一个LLM（或同一模型不同温度）对输出按评分标准打分，设置阈值。注意评分Prompt本身也要版本化，否则评分标准漂移会污染测试结果。

测试数据集要覆盖：正常路径、边界输入（空上下文、超长query）、对抗输入（注入指令）、以及历史bug案例。每次修改Prompt，跑全量回归，记录通过率。

一个常见的坑：测试用例的期望输出是硬编码的。当业务需求变化时，需要同步更新测试用例，否则测试会变成“防止改进”的枷锁。我的做法是把测试用例和Prompt放在同一个PR里评审。

## 可观测性：线上行为的显微镜

Prompt上线后，你需要知道它实际表现如何。至少记录：

- **每次调用的输入变量哈希**（避免存储敏感原文）、渲染后的Prompt长度（token数）、模型名称与版本、温度等参数。
- **输出结构校验结果**、是否触发重试、延迟、token消耗。
- **用户反馈信号**（如点赞/点踩、后续修正）。

这些数据可以回答：新版本Prompt是否导致输出长度暴涨？某个变量缺失是否与错误率上升相关？哪些输入模式容易触发模型拒绝回答？

我习惯在日志里加一个 `prompt_version` 字段，这样在Grafana里可以按版本切分指标。没有这个字段，A/B测试和故障排查会非常痛苦。

## 失败模式与权衡

- **过度版本化**：每个标点修改都升版本，导致版本爆炸。建议只对影响契约的变更升版本，措辞优化可以合并到修订号。
- **回归测试过严**：用精确匹配导致每次模型升级都失败。应聚焦结构和不变量。
- **可观测性成本**：记录全量Prompt会存储爆炸且涉及隐私。建议只存哈希和长度，必要时采样存储脱敏后的文本。

## 开放问题

如何自动化发现Prompt的“隐性契约”？比如模型在特定输入下会忽略输出格式要求。目前我靠人工构造对抗用例，还没找到通用的静态分析方法。另一个问题是多轮对话中，Prompt的版本如何与对话状态绑定——是每轮用最新版本，还是整个会话固定一个版本？我倾向于后者，但需要更细粒度的会话管理。

把Prompt当接口，意味着接受软件工程的那套纪律。这不会让模型更聪明，但能让系统更可控。
