很多团队把 prompt 当成字符串常量：改完直接上线，出问题再回滚。但 prompt 实际是模型与业务逻辑之间的接口，它定义了输入契约、输出格式和失败模式。把它当接口管理，需要版本控制、回归测试和可观测性。

**版本控制：不只是 git commit**

prompt 的版本要绑定模型版本、解码参数（temperature、top_p、max_tokens）和函数 schema。同一个 prompt 在 gpt-4o 和 gpt-4o-mini 上行为可能完全不同。我习惯用结构化文件存储：

```yaml
id: surg-agent-answer
version: 3
model: gpt-4o-2024-08-06
temperature: 0.2
max_tokens: 1024
messages:
  - role: system
    content: |
      你是手术辅助助手。只根据提供的上下文回答。
      如果上下文不足，回答“无法确定”。
  - role: user
    content: |
      上下文：{{context}}
      问题：{{question}}
output_schema: answer_v1.json
```

这样每次请求日志里可以记录 `prompt_id` 和 `version`，回滚时只需切换版本号，而不是重新部署代码。

**回归测试：用真实失败案例构建数据集**

prompt 的单元测试不是断言字符串相等，而是断言行为。我通常维护一个 JSONL 测试集，每条包含输入、期望输出类型和检查函数。例如：

```json
{"input": {"context": "...", "question": "出血量多少？"}, "assert": "contains_any", "values": ["无法确定", "未提供"]}
```

检查函数可以是：JSON schema 校验、关键实体是否存在、是否包含禁止词、是否调用了正确的函数。每次修改 prompt 后跑一遍，观察通过率变化。注意：LLM 输出有随机性，建议 temperature=0 跑 3 次取多数，或对每个用例设置容差。

**可观测性：记录 token、延迟和失败模式**

线上请求要记录：prompt 版本、模型、输入 token 数、输出 token 数、首 token 延迟、总延迟、是否触发函数调用、是否解析失败。这些指标能回答：新版本是否让输出变长？是否增加了 JSON 解析失败率？

我还会对输出做轻量级分类：完全符合 schema、部分符合、解析失败、拒绝回答。当解析失败率超过 1% 时告警。另一个有用的指标是“上下文利用率”：检索到的 chunk 有多少被模型引用。如果引用率低于 20%，可能是检索或 prompt 有问题。

**边界与失败模式**

- 上下文超长时，模型可能忽略中间部分。需要分块或摘要，并测试不同位置的信息召回率。
- 函数调用 schema 变更后，旧 prompt 可能生成不存在的参数。版本绑定能避免。
- 多轮对话中，历史消息会挤占 token 预算。需要显式截断策略，并测试截断后的行为。
- 模型升级（如 gpt-4o 到 gpt-4o-2024-11-20）可能改变输出风格。回归测试要覆盖模型版本切换。

**一个未解决的问题**

如何自动化生成高质量的回归测试用例？目前我靠人工收集线上失败案例，但覆盖度有限。也许可以用另一个 LLM 对失败输出做变异生成，但如何保证变异后的用例仍然有效，我还没找到好方法。

把 prompt 当接口，不是增加官僚流程，而是让迭代更安全。版本、测试、观测三件套，能让你在改一个词之前就知道可能的影响。
