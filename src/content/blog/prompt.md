## 为什么 prompt 是接口，不是配置

我最初把 prompt 写在 YAML 里，改完直接上线。结果一次“优化”让 RAG 的引用率从 92% 掉到 67%，三天后才发现。问题在于：prompt 定义了模型行为的契约——输入什么、输出什么格式、失败时怎么退。它和函数签名一样，需要版本、测试和监控。

## 版本化：别用 git 当唯一真相

git 能存历史，但回答不了“线上现在跑的是哪版”。我的做法：

- 每个 prompt 模板有 `id`、`version`（semver）、`hash`（内容 sha256）。
- 模板存数据库，发布走审批流；git 只存种子和迁移脚本。
- 请求日志里记录 `prompt_id + version + hash`，这样任何一条输出都能追溯到确切模板。

一次事故：同事热修了模板但没 bump version，导致 A/B 实验组混淆。后来强制 CI 检查：内容变则 hash 变，hash 变则 version 必须变。

## 回归测试：用“金标准集”而不是感觉

Prompt 改动最怕“看起来更好”。我维护一个 200 条的回归集，覆盖：

- 正常问答（含多跳）
- 边界：空检索、超长上下文、多语言混杂
- 对抗：诱导越狱、要求编造引用
- 格式：必须输出 JSON 且字段完整

评估不只看准确率，还看：

- **引用忠实度**：答案中的每个事实是否能在检索片段中找到支撑（用 NLI 模型或规则匹配）。
- **格式合规率**：JSON 解析失败率。
- **token 成本**：平均输入/输出 token，防止 prompt 膨胀。
- **延迟 P95**：prompt 变长会推高首 token 时间。

跑一次全量回归约 8 分钟、成本 3 美元，比线上事故便宜。

## 可观测性：记录什么、怎么采样

线上我记录：

- 输入：用户 query、检索到的 chunk id 与分数、最终 prompt 的 hash。
- 输出：原始文本、解析后结构、token 数、延迟。
- 反馈：用户点赞/点踩、是否复制、是否追问。

采样策略：全量记录元数据（轻量），对 5% 请求存完整 prompt/response（注意脱敏）。这样既能做聚合监控，又能事后 debug。

监控面板看四个指标：格式失败率、引用缺失率、P95 延迟、每请求成本。任一超过阈值就告警。

## 一个具体例子：Surg-Agent 的 JSON 输出

手术问答 agent 要求输出 `{answer, citations, confidence}`。早期 prompt 说“请引用来源”，模型经常编造 `[1]` 但检索里没有。改成：

```
只允许引用以下片段编号：{{chunk_ids}}
若无法回答，输出 {"answer":"","citations":[],"confidence":0}
```

回归集里加了 30 条“无答案”样本，强制模型学会拒答。格式失败率从 11% 降到 1.2%。

## 未解问题

- 回归集会过拟合：改 prompt 去迎合测试，线上泛化反而差。怎么自动扩充？
- 多轮对话的版本追踪：每轮 prompt 都不同，怎么归因？
- 小模型上 prompt 的鲁棒性更差，同一模板换模型要不要重新回归？

我的结论：把 prompt 当接口，用工程手段管起来，比追求“神级 prompt”更可持续。
