很多人第一次做 RAG，都会盯着向量检索返回的 `score` 问：0.82 算高吗？能不能设 0.75 做阈值？我的回答通常是：先别急着定阈值，先搞清楚这个分数是怎么算出来的。

## 相似度分数只是几何量，不是概率

以最常见的余弦相似度为例，它衡量的是两个向量在空间中的夹角：

```
cos(a, b) = (a · b) / (||a|| * ||b||)
```

它落在 [-1, 1]，但实际 embedding 模型（尤其是对比学习训练的）输出往往集中在很窄的区间，比如 0.6 到 0.95。不同模型、不同归一化方式、甚至不同语言，分布都不同。所以“0.8 算不算相似”没有跨模型的意义。

更关键的是：**余弦相似度不是“相关概率”**。它没有经过校准，不能解释为“这两个文本有 80% 的概率相关”。如果你拿它当置信度做阈值过滤，很容易在分布偏移时翻车。

## 分数可比性的三个前提

分数要能比较，至少需要满足：

1. **同一个模型、同一版本**。换模型或微调后，分数分布会整体漂移，旧阈值直接失效。
2. **同一归一化与距离度量**。有些向量库默认用内积（IP），有些用 L2。归一化后 L2 和余弦等价，但没归一化时结果不同。
3. **同一查询分布**。短查询和长文档的 embedding 分布不一样，跨类型比较分数没有意义。

我见过一个典型 bug：索引时用了 `normalize=True`，查询时忘了归一化，内积分数整体偏大，阈值形同虚设。

## 阈值应该怎么定

不要拍脑袋。可行做法是：

- 构造一个小的标注集（比如 200 条 query，每条标出相关 chunk），计算正负样本的分数分布，看重叠区域。
- 用 precision-recall 曲线选阈值，而不是看单一分数。如果业务不能容忍误召回，阈值往高走；如果召回优先，就放宽，靠 rerank 兜底。
- 监控线上分数分布。如果某天查询分数整体下移，可能是 embedding 服务版本变了，或者用户 query 风格变了。

一个实践细节：**top-k 的绝对分数不如相对排序稳定**。与其卡 0.75，不如取 top-20 再用 cross-encoder rerank，让 reranker 给一个更可解释的相关性分数。

## 相似 ≠ 有用

这是最容易忽略的一点。embedding 相似度衡量的是语义接近，但检索要的是“能回答问题”。两个反例：

- 查询“术后感染怎么处理”，最相似的 chunk 可能是“术后感染的发生率是 5%”，语义很近，但对回答没用。
- 否定句：“不需要预防性使用抗生素”和“需要预防性使用抗生素”在 embedding 空间里可能非常接近。

所以纯向量检索在医疗、法律这类需要精确逻辑的场景，必须配合关键词检索（BM25）做混合召回，再用 rerank 做精排。

## 分块与 embedding 的耦合

chunk 大小直接影响分数含义。chunk 太大，一个向量要平均太多主题，相似度被稀释；chunk 太小，缺乏上下文，embedding 本身就不准。我的经验是：

- 先按语义边界切（段落、标题），再控制 token 数（比如 256-512 tokens），保留 10%-20% 重叠。
- 对表格、代码这类结构，单独处理，别硬塞进通用 embedding。
- 给每个 chunk 加上来源标题或章节路径再 embedding，能显著提升可检索性。

## 一个开放问题

我现在还没想清楚的是：**如何给 embedding 分数做轻量校准**。比如用一个小型逻辑回归把原始分数映射到校准后的相关性概率，理论上可行，但需要标注数据，而且换模型就得重训。有没有更鲁棒的无监督方法，我还在试。

总之，把相似度分数当成一个排序信号，而不是一个概率或真理。理解它的几何本质和分布特性，比调阈值更重要。
