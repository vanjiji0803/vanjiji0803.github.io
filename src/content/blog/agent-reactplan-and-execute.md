做 Surg-Agent 那段时间，我最常被问的问题是：为什么不用 ReAct 一把梭？我的回答通常是：ReAct 在第三步之后就开始忘事。这篇文章把三种规划范式的机制、开销和崩溃点摊开讲，尽量给可落地的判断依据。

## ReAct：把规划藏在每一步的 thought 里

ReAct 的本质是「思考-行动-观察」循环，规划不是显式的数据结构，而是每轮 prompt 里由模型临时生成的 thought。实现上通常是一个 while 循环：拼接历史 → 调模型 → 解析出 tool call → 执行 → 把 observation 追加回上下文。

它的优点是零额外结构，对开放式任务友好。代价是上下文线性膨胀。假设每轮 thought + action + observation 平均 300 token，10 轮就是 3000 token，加上 system prompt 和工具描述，很容易吃掉 8k 上下文的一半。更麻烦的是「目标漂移」：第 7 轮时模型看到的开头是原始问题，中间夹着 6 轮无关观察，它很容易把某个中间结果当成最终目标。我在手术视频检索里遇到过：用户问「找出出血片段」，ReAct 在第 4 轮开始反复调用 `search_clip` 而不是 `detect_bleeding`，因为前几轮的检索结果里「出血」这个词出现频率最高。

缓解手段：每 N 轮做一次上下文压缩（把历史 observation 摘要成一句），或者给循环加硬上限并在超限时强制走 fallback。但压缩本身会丢信息，这是个 tradeoff，没有免费午餐。

## Plan-and-Execute：先出 DAG，再逐节点执行

这类范式把规划显式化：先让模型输出一个步骤列表（最好是带依赖的 DAG），再由 executor 按拓扑序执行，每步只带必要的上下文。好处是 token 可控——每个子任务独立构造 prompt，不被无关历史污染；也便于并行和重试。

崩溃点有三个。第一，**规划质量与执行反馈脱节**：初始 plan 是基于「没有执行结果」的假设生成的，一旦第 2 步返回意外结果，后续步骤可能整体失效。常见补丁是 replan：每执行完一个节点，判断是否需要重规划。但 replan 太频繁就退化成 ReAct，太少又僵化。第二，**步骤粒度过粗**：如果一步是「分析所有视频」，executor 内部又变成一个小 ReAct，token 问题原样复现。第三，**依赖表达**：让模型输出合法 DAG 比输出线性列表难得多，我见过不少 JSON 里出现环或引用不存在的节点，需要 schema 校验 + 重试。

实践上我倾向「线性 plan + 每步带验收条件」：每步写清楚输入、输出和成功判据，executor 只负责执行和判定，重规划由外层状态机触发。

## 状态机：把控制流从模型手里拿走

状态机不是让模型规划，而是人预先定义状态和转移，模型只在状态内做局部决策。Surg-Agent 的手术阶段导航就是这种：`idle → localize → detect → verify → report`，每个状态有明确的进入条件、可用工具和退出条件。

优点是可控、可观测、可测试——每个状态可以单独写单测，延迟可预测。缺点是灵活性差，遇到状态机没覆盖的路径就卡死。所以状态机适合「流程稳定、容错要求高」的场景，比如医疗、金融审批；不适合开放式研究型任务。另一个坑是状态爆炸：状态一多，转移表维护成本指数上升，需要定期清理不可达状态。

## 怎么选：看三个维度

我的经验是按「任务开放性 × 容错成本 × 上下文预算」来选。开放且容错高、预算充足 → ReAct；任务可分解、需要并行 → Plan-and-Execute；流程固定、错误代价高 → 状态机。混合也常见：外层状态机管阶段，阶段内用 ReAct 处理局部不确定性。

评估上，别只看最终答案对不对。我通常记录：每任务轮数分布、token 消耗、工具调用成功率、重规划次数、以及人工标注的「目标漂移」比例。这些指标比单一准确率更能暴露规划器的真实问题。

最后留个开放问题：目前还没有一个轻量方法能在运行时判断「当前 plan 是否已经失效」，多数靠启发式阈值。这块我还没找到满意的方案。
