最近在做一个 RAG 的 Agent 系统，需要让模型调用检索、重排、摘要等工具。一开始我图省事，把参数设计得很随意，结果发现 agent 的行为非常不稳定：明明给足了上下文，它却频繁调用错误的工具，或者传错参数。后来仔细排查，发现问题大多出在函数调用的 schema 设计上。

## 参数命名：别让模型猜

LLM 在生成函数调用时，本质上是根据自然语言描述去匹配参数名。如果你的参数名模糊，比如用 `data`、`info`、`value`，模型就很容易把用户问题中的关键词填进去，导致语义错位。

举个例子，我有一个检索工具，参数原本是 `query` 和 `top_k`。但用户问题里可能包含“最近”这样的时间词，模型可能就把“最近”当作 `query` 的一部分，而不是理解为时间过滤。后来我把参数改成 `query_text` 和 `time_range`，并在描述里明确说明 `time_range` 接受 ISO 格式的日期范围，模型的表现就稳定多了。

**经验：** 参数名要具体，最好带上类型或语义后缀（如 `_text`、`_id`、`_range`），描述里写清楚格式和示例。

## 类型与格式：约束要硬

LLM 生成 JSON 时，对类型的把握并不总是可靠。如果你允许 `string` 类型，但内部逻辑需要整数，模型可能输出 `"5"` 而不是 `5`，或者输出 `"5.0"`。这会导致解析错误或边界问题。

我在设计 schema 时，尽量使用严格的类型，并在描述中给出示例。比如 `top_k` 用 `integer`，并注明 `1-20`。但即使这样，模型有时仍会输出 `"10"`。所以我在代码里做了防御性转换：如果类型是整数，但收到字符串，就尝试 `int()`，失败则返回错误。

**更关键的是枚举值。** 如果你的参数只接受固定几个选项，一定要用 `enum` 约束。我之前有个工具参数 `sort_order`，允许 `"asc"` 或 `"desc"`，但模型偶尔会输出 `"ascending"` 或 `"descending"`，导致校验失败。后来我加了 `enum`，模型就很少犯错了。

## 必填与可选：别让模型自作主张

并不是所有参数都需要必填。如果某个参数是可选的，但你没在描述里说清楚，模型可能会“脑补”一个值，或者干脆不传。这会导致两种失败：

- 模型传了多余参数，但你的函数不接受（忽略或报错）。
- 模型没传必填参数，导致函数无法执行。

我遇到过最典型的情况：检索工具需要一个 `collection_id` 来指定索引，但用户问题里没提，模型就没传。后来我在描述里写明“如果未指定，默认使用主集合”，并把 `collection_id` 设为可选，在函数内部处理默认值。这样既减少了模型决策负担，也避免了因缺失参数导致的失败。

**建议：** 每个参数都要明确标注是否必填，并在描述中说明默认行为。对于可选参数，最好在函数内部提供合理的默认值，而不是依赖模型。

## 描述：少一点抽象，多一点具体

描述是模型理解参数语义的唯一来源。如果你只写“查询文本”，模型可能不理解它应该包含什么。更好的写法是：“用户的自然语言查询，例如‘最近一周关于阿司匹林的论文’”。

我甚至会在描述里写反例：“不要包含过滤条件，过滤条件请使用 `filter` 参数”。这能有效防止模型把过滤词塞进查询里。

## 失败模式与调试

即使 schema 设计得再好，模型仍可能出错。我总结了常见的失败模式：

1. **参数名拼写错误**：模型可能把 `query_text` 写成 `queryText`。解决：在代码中做别名映射，或者使用宽松的解析（如 `jq` 的 `--arg` 方式）。
2. **多余参数**：模型可能传了 schema 中没有的参数。解决：在解析时忽略未知字段，而不是报错。
3. **值类型错误**：如上面提到的字符串数字问题。解决：写一个通用的类型转换函数，根据 schema 定义做强制转换。

调试时，我会记录模型生成的原始 JSON 和最终解析结果，方便定位是模型问题还是解析问题。我甚至会在日志里打印出 schema 的校验错误信息，帮助快速定位。

## 评估：别只看成功率

评估函数调用的质量，不能只看是否成功执行。我通常会统计：

- **参数正确率**：生成的参数是否与预期一致（比如 top_k 是否在范围内）。
- **无效调用率**：模型是否调用了不存在的函数或传了无效参数。
- **重试率**：因为参数错误导致的重新生成次数。

这些指标能反映 schema 设计的合理性。如果无效调用率高，说明描述或约束不够清晰。

## 未解的问题

目前我还在探索如何让模型更好地理解嵌套参数（比如对象数组）。对于复杂工具，比如检索后处理，参数可能是一个包含多个过滤条件的结构。我尝试过用 JSON Schema 的 `additionalProperties` 和 `oneOf`，但模型有时会生成不符合结构的 JSON。也许需要更细粒度的描述，或者干脆把复杂逻辑拆分成多个简单工具。

另一个问题是：当工具很多时，模型容易混淆相似参数。比如我有 `search` 和 `search_web` 两个工具，参数类似，模型有时会选错。我考虑过在描述中强调差异，但效果有限。也许需要更严格的命名区分，或者引入工具选择器（router）来预筛选。

## 总结

函数调用的 schema 设计是 Agent 工程中容易被忽视但至关重要的环节。参数命名要具体，类型要严格，描述要清晰，必填可选要明确。同时，要在代码中做防御性解析，并记录日志以便调试。最后，用参数正确率、无效调用率等指标来持续优化 schema。

如果你也在做类似的 Agent，建议花时间仔细打磨每个工具的 schema，这比调 prompt 更有效。毕竟，模型是照着 schema 来“思考”的。
