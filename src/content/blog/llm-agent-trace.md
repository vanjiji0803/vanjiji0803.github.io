最近在开发 Surg-Agent（一个基于 RAG 的手术智能体）时，我深刻体会到：构建 LLM Agent 的难度不在于写代码，而在于调试。当 Agent 在复杂任务中表现不佳时，你很难知道是 prompt 写错了、工具调用失败了、还是上下文检索出了问题。传统的日志和监控在这里几乎失效，因为 LLM 的输出是概率性的，错误往往不是异常，而是“看似合理但实际错误”。

这篇文章我想分享我在 Agent 可观测性上的一些实践，特别是 trace、span、prompt 记录、工具输出捕获，以及一套失败分类框架。这些经验来自我部署在 NVIDIA IGX 上的手术 Agent，但原理是通用的。

## 为什么传统日志不够用？

传统后端服务中，日志是结构化的，错误是明确的（如 HTTP 500、数据库连接失败）。但 LLM Agent 的每次调用都是非确定性的，即使输入相同，输出也可能不同。更重要的是，Agent 的决策链很长：它可能先调用工具获取信息，然后基于这些信息做出推理，再调用另一个工具……任何一个环节的微小偏差都可能导致最终结果错误。

传统日志只能告诉你“发生了什么”，但无法告诉你“为什么发生”。你需要看到完整的上下文：用户请求、Agent 的思考过程、每一步的工具调用、工具的返回结果、以及最终的输出。这就是 trace 的价值。

## Trace 和 Span：构建完整的调用链

Trace 是 Agent 处理一个请求的完整生命周期，Span 是其中的一个步骤。例如，一个典型的手术 Agent 请求可能包含以下 span：

1. **用户输入处理**：解析用户的自然语言请求，提取意图。
2. **检索增强生成（RAG）**：根据请求检索手术指南、解剖学知识等。
3. **工具调用**：调用手术器械数据库、患者病历系统等。
4. **推理与规划**：LLM 基于所有信息生成行动计划。
5. **最终响应生成**：将计划转换为自然语言回复。

每个 span 都应该记录：开始时间、结束时间、输入、输出、以及元数据（如模型名称、温度、token 数）。这样，当 Agent 出错时，你可以快速定位是哪个环节出了问题。

**具体实现**：我使用 OpenTelemetry 作为基础框架，自定义了 LLM Span 和工具 Span。LLM Span 记录 prompt、completion、token 计数、延迟；工具 Span 记录工具名称、输入参数、输出结果。所有 span 通过 trace ID 关联，存储在 Elasticsearch 中，用 Kibana 可视化。

## Prompt 和工具输出的记录：细节是魔鬼

记录 prompt 和工具输出是调试的关键，但也是最容易忽略的。很多框架默认只记录最终结果，但中间步骤的 prompt 往往包含动态注入的上下文（如检索到的文档），这些上下文可能包含噪声或误导信息。

**我的实践**：每个 LLM Span 都保存完整的 prompt（包括 system prompt、few-shot examples、动态上下文）和 completion。这会占用大量存储，但为了调试，值得。我使用日志轮转策略，只保留最近 7 天的数据，并对敏感信息进行脱敏。

工具输出同样重要。工具返回的数据可能被截断、格式错误、或包含意外值。例如，我的手术器械数据库返回了一个 JSON，但某个字段是 null，导致 LLM 在后续推理中产生了幻觉。如果没有记录工具输出，你很难发现这个根因。

**一个具体例子**：有一次，Agent 在回答“如何缝合血管”时，给出了错误的手术步骤。通过查看 trace，我发现它调用的“手术指南检索”工具返回了一篇关于“血管吻合”的综述，但其中包含的步骤是过时的。问题不在 LLM，而在检索结果的质量。这个案例让我意识到，工具输出的质量直接影响 Agent 的可靠性，而 trace 能帮你快速定位这种问题。

## 失败分类：从“它错了”到“为什么错”

仅仅记录 trace 还不够，你还需要一套分类体系来归纳失败模式。我根据经验将 LLM Agent 的失败分为以下几类：

1. **工具调用失败**：工具本身出错（如 API 超时、返回错误码）。
   - 处理：重试机制、降级策略。
2. **上下文检索失败**：RAG 检索到的文档不相关或信息过时。
   - 处理：改进嵌入模型、调整 chunk 大小、增加 rerank。
3. **规划失败**：Agent 制定了错误的行动计划，例如步骤顺序颠倒。
   - 处理：增加规划提示、使用更强大的模型、引入人工审核。
4. **推理失败**：LLM 在逻辑推理上出错，例如混淆了概念。
   - 处理：改进 prompt、增加 few-shot 示例、使用思维链。
5. **幻觉**：LLM 生成了看似合理但错误的信息。
   - 处理：增加事实核查、限制输出范围、使用外部知识库。
6. **用户意图误解**：Agent 没有正确理解用户请求。
   - 处理：增加意图识别模块、提供澄清选项。

**我的分类实践**：在 Surg-Agent 中，我定义了一个 `FailureCategory` 枚举，并在每次失败时通过一个分类函数自动打标签。这个函数会分析 trace 中的错误类型、工具返回状态、以及 LLM 输出与期望的匹配度。然后，我定期统计各类失败的占比，优先解决高频问题。

例如，如果“上下文检索失败”占 40%，我会优先优化检索模块，而不是调整 prompt。这种数据驱动的决策方式比凭感觉调参有效得多。

## 评估与监控：从日志到指标

除了 trace，我还建立了几个关键指标：

- **成功率**：Agent 成功完成任务的百分比。
- **平均延迟**：每个 span 的延迟，特别是 LLM 调用和工具调用。
- **Token 消耗**：每个请求的 token 数，用于成本控制。
- **失败分布**：各类失败的占比，用于指导优化。

这些指标通过 Prometheus 收集，在 Grafana 中展示。我设置了告警规则，例如当成功率低于 80% 时触发告警。

**评估方法**：对于 Agent 的评估，我使用两种方式：离线评估和在线评估。离线评估使用一组标注好的测试用例，自动运行 Agent 并比对输出；在线评估则收集真实用户的反馈（如点赞/点踩）。离线评估可以快速迭代，在线评估能发现长尾问题。

## 开放问题与未来方向

尽管 trace 和失败分类已经大大提升了我的调试效率，但仍有一些未解决的问题：

- **如何自动修复失败？** 目前我只能根据分类手动调整，未来希望实现自动化的 prompt 优化或工具选择。
- **如何评估多轮对话的 Agent？** 单轮评估容易，但多轮对话的上下文依赖性强，评估难度大。
- **如何降低 trace 存储成本？** 保存所有 prompt 和输出会消耗大量存储，我正在尝试采样策略，只记录失败案例的完整 trace。

如果你有类似经验，欢迎交流。可观测性是 Agent 工程中不可忽视的一环，它决定了你能否快速迭代和信任你的系统。
