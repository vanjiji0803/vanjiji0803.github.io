最近在给 Surg-Agent 加可观测性，踩了不少坑。LLM Agent 不是单体服务，它是一张动态生成的调用图：LLM 推理、工具调用、外部 API、内部状态转移，全都交织在一起。出了问题，你根本不知道是模型抽风、工具返回脏数据，还是状态机逻辑写错了。

这篇文章聊聊我在实践中总结的 Trace/Span 设计、Prompt 和工具输出的记录方式，以及一套失败分类法。

## Trace 和 Span：还原 Agent 的决策路径

Agent 的每次运行都应该对应一个 Trace，而 Trace 里的每个逻辑单元都是一个 Span。我习惯把 Span 分成四类：

1. **LLM Span**：记录模型名、temperature、输入 tokens、输出 tokens、推理耗时。
2. **Tool Span**：记录工具名、输入参数、输出结果（截断或摘要）、耗时。
3. **State Span**：记录 Agent 的状态转移，比如从 `planning` 到 `executing`，或者 RAG 检索前后的上下文变化。
4. **Flow Span**：用于包裹整个循环或子流程，比如 ReAct 的一轮迭代。

关键点：**Span 必须包含父子关系**。比如，一个 Tool Span 应该挂在触发它的 LLM Span 下面，这样你才能看到“模型决定调用哪个工具”的完整因果链。

另一个容易被忽略的是 **时序**。LLM 推理是秒级，工具调用是毫秒级，但工具可能因为网络超时拖到几十秒。我习惯在每个 Span 里记录 `start_time` 和 `end_time`，并在 UI 里用瀑布图展示。这样一眼就能看出瓶颈在哪。

## Prompt 和工具输出：别只记日志

很多团队只记录 LLM 的输入输出，但 Prompt 是动态拼出来的，里面可能塞了检索到的文档、历史对话、工具描述。不记录完整的 Prompt，你没法复现“模型为什么这么回答”。

我的做法是：

- **Prompt 快照**：把最终发给模型的完整 Prompt 存下来，包含 system prompt、user message、工具定义（functions schema）。
- **工具输出摘要**：工具输出可能很大（比如 RAG 检索回来的 10 个 chunk），全存下来太占空间。我会存一个截断版本（比如前 2000 字符），并附上完整输出的哈希值。调试时如果需要，可以用哈希去检索原始数据。
- **结构化字段**：把模型名、temperature、top_p 这些采样参数也存进 Span，方便对比不同参数下的行为差异。

另外，**工具调用参数**必须单独存。比如 `search_web(query)` 的 query 值，如果只存在 Prompt 里，解析日志会非常痛苦。

## 失败分类：从玄学变成工程

我总结了一套失败分类法，按“故障点”划分：

1. **LLM 输出格式错误**：模型返回的 JSON 解析失败，或者工具调用参数不符合 schema。这是最常见的，通常靠 prompt 优化或增加重试解决。
2. **工具执行错误**：工具本身抛异常，比如 API 超时、数据库连接失败。这类错误要区分“可重试”和“不可重试”，可重试的（如超时）可以自动重试，不可重试的（如参数非法）要直接反馈给模型修正。
3. **上下文超限**：Prompt 超过模型上下文窗口。我见过很多 Agent 在长对话后突然“失忆”，其实就是 context 被截断了。要监控 token 使用量，提前做摘要或裁剪。
4. **状态机非法转移**：Agent 尝试从当前状态跳到一个不允许的状态。这通常是代码 bug，而不是模型问题。
5. **幻觉/错误推理**：模型给出了看似合理但实际错误的工具调用。这类最难检测，我目前的做法是加一层“验证器”，比如对工具输出做规则校验，或者用另一个 LLM 做交叉验证。

在 Trace 里，我会给每个 Span 打上 `status`（ok/error）和 `error_type`，错误信息单独存。这样聚合时，可以直接按 `error_type` 分组，统计各类失败的占比。

## 评估和迭代

可观测性不只是事后排查，还要用于评估。我会把 Trace 导出成 JSON，然后写脚本分析：

- **工具调用成功率**：每个工具的成功率，失败原因分布。
- **平均迭代轮数**：Agent 完成任务需要多少轮 ReAct 循环，轮数多可能意味着 prompt 不清晰或工具设计不合理。
- **Token 消耗**：每次任务的 token 总量，以及 LLM 推理和工具调用各自占多少。

这些指标能直接指导优化。比如，如果发现某个工具经常失败，我会检查它的 schema 是否清晰，或者是否应该拆成更细的工具。

## 还没做的

我还没做的是自动异常检测。目前都是靠人看 Trace 找问题，理想情况是能基于历史 Trace 训练一个模型，自动标记异常行为。但这需要大量标注数据，我还没想好怎么低成本获取。

另外，跨 Trace 的关联分析也还没做。比如，多个 Trace 都调用了同一个外部 API，我想知道这个 API 的整体延迟和错误率，但目前的 Trace 结构是单次的，没法直接聚合。

## 小结

可观测性不是锦上添花，而是 LLM Agent 上生产的前提。Trace/Span 结构、Prompt 快照、失败分类，这三样东西能让你从“盲人摸象”变成“拿着 X 光片看病”。工程上的投入是值得的。
