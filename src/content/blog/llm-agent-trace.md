## 为什么 Agent 的可观测性比传统服务更难

传统微服务里，一个请求的失败通常有明确的错误码和堆栈。但 LLM Agent 的失败是「静默」的：模型可能返回一个语法完全正确、但语义错误的 JSON；工具调用可能成功执行，但参数是幻觉出来的；多步规划可能在第 3 步就偏离了目标，直到第 10 步才暴露。更麻烦的是，Agent 的行为是概率性的——同一个 prompt，两次运行可能走完全不同的路径。

所以，可观测性不是「加个日志」那么简单。我们需要把 Agent 的执行过程拆解成可追踪的单元，并定义一套失败分类，让问题可以被定位、聚合和回归测试。

## Trace 与 Span 的粒度设计

我习惯把一次 Agent 运行（run）作为一个 trace，内部的每个步骤作为 span。关键问题是：span 的粒度多细才合适？

太粗（比如整个 run 一个 span）无法定位问题；太细（每个 token 一个 span）会产生海量数据，且大部分是噪声。我的经验是至少拆成以下几类 span：

- **LLM 调用 span**：记录模型名、输入 token 数、输出 token 数、延迟、finish_reason、是否触发 function call。
- **工具调用 span**：记录工具名、参数（脱敏后）、返回状态、执行耗时、返回内容摘要。
- **检索 span**：记录 query、top-k、每个 chunk 的 score、rerank 后的顺序。
- **规划/决策 span**：如果 Agent 有显式的 planner，记录它输出的计划或下一步动作。

这些 span 通过 trace_id 和 parent_span_id 串起来，形成一棵调用树。对于多轮对话，还要加上 session_id 和 turn_index，否则无法区分「同一轮内的多步」和「跨轮的历史」。

一个容易忽略的点：**prompt 的版本**。每次 LLM 调用都应该记录实际发送的完整 prompt（或至少其 hash 和模板版本）。否则当 prompt 被修改后，你无法判断性能变化是模型问题还是 prompt 问题。

## 记录什么：prompt、工具输出与状态快照

记录完整 prompt 会带来存储成本和隐私问题。我的做法是分级：

- **生产环境**：记录 prompt 的 hash、模板 ID、变量摘要（如检索到的文档 ID 列表），以及 token 数。不记录原始文本。
- **调试/采样环境**：对少量请求（比如 1%）记录完整 prompt 和工具输出，用于深度分析。
- **敏感字段**：工具参数中的用户 ID、病历号等，在记录前做脱敏或哈希。

工具输出同样需要摘要。一个工具可能返回 10KB 的 JSON，但真正影响决策的往往只是其中几个字段。我会记录：返回状态、耗时、输出长度、以及一个可配置的「关键字段提取器」的结果。这样既能定位问题，又不会让 trace 变成数据仓库。

另外，**状态快照**很重要。Agent 通常维护一个内部状态（如对话历史、已执行的动作列表）。在每个 span 结束时记录状态的关键部分（比如当前目标、已用工具列表），可以快速判断 Agent 是否「迷路」。

## 失败分类：从「报错」到「可操作的标签」

可观测性的最终目的是定位和修复问题。我倾向于把失败分成几大类，每类对应不同的排查方向：

1. **模型输出格式错误**：JSON 解析失败、缺少必填字段、类型错误。这类问题通常通过更严格的 prompt 或输出解析器重试来解决。
2. **工具调用错误**：参数错误（如幻觉出不存在的 ID）、工具执行超时、工具返回业务错误。需要区分是模型生成参数的问题，还是工具本身的问题。
3. **检索失败**：检索不到相关文档（recall 低）、检索到无关文档（precision 低）、或 rerank 后顺序错误。这类问题要回溯到 embedding 和 chunking 策略。
4. **规划失败**：Agent 选择了错误的下一步动作，或陷入循环（重复调用同一工具）。可以通过检测连续重复的 span 来告警。
5. **幻觉与事实错误**：模型生成了看似合理但实际错误的内容，且没有工具调用去验证。这类最难自动检测，通常需要人工评估或基于规则的校验（如检查引用的文档是否存在）。
6. **上下文溢出**：prompt 超过模型上下文窗口，导致截断或报错。需要监控 token 使用趋势。

每个失败事件都应该打上这些标签，并关联到具体的 span。这样你可以做聚合分析：比如「过去 24 小时，工具调用错误中 60% 是参数幻觉，主要集中在 get_patient_info 这个工具上」。

## 实现细节与权衡

- **采样策略**：全量记录 trace 的元数据（span 类型、耗时、状态），但只对部分 trace 记录完整 payload。采样可以按错误率动态调整：错误率上升时提高采样率。
- **异步写入**：可观测性数据不能阻塞主流程。用队列异步写入，并设置背压策略（如丢弃低优先级 span）。
- **与评估的闭环**：把失败分类的标签反馈到离线评估集，构造针对性的测试用例。比如，如果发现大量「检索失败」，就在评估集中增加需要多跳检索的问题。

## 一个未解决的问题

目前我还没有很好的办法自动区分「规划失败」和「模型能力不足」。两者都表现为 Agent 没有完成任务，但前者可以通过改进 planner prompt 或增加约束来缓解，后者可能需要换模型或微调。也许可以通过对比同一任务在不同模型上的 span 序列来辅助判断，但这需要大量标注数据。如果你有相关经验，欢迎交流。

可观测性不是一次性的工作，而是随着 Agent 复杂度增长持续迭代的基础设施。从最简单的 trace 开始，逐步补充 span 类型和失败标签，比一开始就追求大而全更实际。
