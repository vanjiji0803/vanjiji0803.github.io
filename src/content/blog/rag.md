在构建 RAG 系统时，我们常把大量精力花在选向量库、调索引参数上，却容易忽略一个事实：**最终决定生成质量的是喂给 LLM 的上下文，而重排序（reranking）往往是控制上下文质量最有效的一环**。这篇文章从机制、权衡和实现细节聊聊为什么第二阶段模型经常比向量库本身更重要。

## 向量检索的局限：双塔模型的表达瓶颈

主流向量检索基于双塔（bi-encoder）结构：query 和 document 分别编码为向量，用余弦相似度或内积衡量相关性。这种设计为了支持大规模近似最近邻（ANN）搜索，牺牲了 query 和 document 之间的细粒度交互。两个向量在编码时互不可见，模型只能把语义压缩进一个固定维度的向量里。对于短 query 和长文档，这种压缩损失尤其明显——文档中可能只有一两句话真正相关，但整段文本被平均成一个向量，相似度信号被稀释。

举个例子：query 是“术后吻合口漏的早期识别指标”，一篇文档大段讲手术步骤，只在末尾提了一句“CRP 在术后第 3 天超过 150 mg/L 提示吻合口漏风险”。双塔模型很可能因为文档整体主题是手术而给出中等相似度，排在前 50 名之外。而交叉编码器（cross-encoder）把 query 和文档拼接后一起过 Transformer，能直接建模这种局部匹配，打分更准。

## 重排序的机制：交叉编码器如何工作

重排序模型通常是 cross-encoder：输入 `[CLS] query [SEP] document [SEP]`，输出一个相关性分数。因为 query 和 document 在每一层注意力中都能交互，模型可以捕捉词级对齐、否定、条件关系等细粒度信号。代价是无法预计算文档表示，每个 (query, document) 对都要一次前向传播，所以只能用于对少量候选（比如 top 50~100）做精排。

工程上常见的两阶段流水线：
1. **召回阶段**：用向量库（或 BM25）快速取回 top K（如 100）候选，追求高召回率。
2. **重排序阶段**：用 cross-encoder 对 K 个候选打分，取 top N（如 5~10）送入 LLM。

这里的关键认知是：**召回阶段的目标是“不漏”，重排序阶段的目标是“排准”**。向量库的调参（HNSW 的 M、efConstruction 等）影响的是召回率和延迟，但只要召回集里包含相关文档，重排序就有机会把它捞上来。反之，如果重排序模型弱，即使向量库召回完美，噪声文档也会挤占上下文窗口，导致 LLM 分心或幻觉。

## 权衡：延迟、成本与效果

重排序不是免费的。以一个小型 cross-encoder（如 6 层、110M 参数）为例，在 GPU 上对 100 个候选（每个 512 token）打分，延迟大约在几十毫秒量级；如果换用 12 层、更大的模型，延迟可能翻倍。在边缘设备或高并发场景下，这个开销需要认真评估。

几个实用的折中点：
- **候选数量 K**：从 100 降到 50 能减半重排序开销，但可能损失召回。可以通过分析召回曲线（recall@K）来选 K，通常 K=50 已经能覆盖大部分相关文档。
- **模型大小**：小模型（如 MiniLM 系列）速度快，适合对延迟敏感的场景；大模型（如基于 DeBERTa 的）效果更好，可用于离线或异步场景。
- **批处理**：把 K 个候选拼成一个 batch 做前向，能充分利用 GPU 并行，显著降低平均延迟。
- **缓存**：对高频 query 或固定文档集，可以缓存重排序分数，但要注意 query 分布变化。

另一个常被忽略的点是**重排序模型的领域适配**。通用重排序模型在医疗、法律等垂直领域可能表现不佳，因为术语和相关性定义不同。用领域数据做微调（甚至用 LLM 生成弱标签）往往比换更大的向量模型收益更高。

## 实现细节与失败模式

在实际部署中，我遇到过几个坑：

1. **截断问题**：cross-encoder 有最大长度限制（如 512 token）。长文档被截断后，关键信息可能丢失。解决办法包括：对长文档做段落切分后分别打分取最大，或用滑动窗口。
2. **分数校准**：不同 query 的重排序分数分布不同，直接设固定阈值过滤可能误杀。可以按 query 做归一化（如 softmax 或 min-max），或只取 top N 而不设绝对阈值。
3. **与生成模型的协同**：重排序分数高不代表对生成有用。有时包含答案的文档分数不是最高，但 LLM 需要它。可以尝试把重排序分数作为特征输入给 LLM（如按分数排序并标注），或让 LLM 自己从候选中选。
4. **延迟毛刺**：重排序模型首次加载、显存不足导致的换页都会引起长尾延迟。需要监控 P99 而非只看均值。

## 评估方法

要判断重排序是否值得，不能只看端到端指标。建议分层评估：
- **召回率**：召回阶段 recall@K，确保相关文档在候选集中。
- **重排序质量**：用标注数据计算 NDCG@N 或 MRR，对比不同重排序模型。
- **端到端**：生成答案的准确率、忠实度（faithfulness），以及上下文利用率（多少 token 真正被 LLM 引用）。

如果没有标注数据，可以用 LLM 做相关性判断（LLM-as-a-judge）来构造评估集，但要注意 judge 的偏差。

## 开放问题

重排序与向量库的关系有点像“精排与粗排”的经典架构。但 RAG 场景下有个新问题：**重排序模型和生成模型都是 LLM 时，能否用生成模型本身做重排序？** 比如让 LLM 对候选文档逐一点评相关性，或利用其内部注意力。这能省掉一个模型，但延迟和成本可能更高。我还没在生产环境试过，值得探索。

总之，如果你的 RAG 效果不佳，在换向量库之前，先看看重排序阶段——它可能才是瓶颈所在。
