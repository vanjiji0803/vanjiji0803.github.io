很多人把 RAG 当成“把文档切一切、塞进向量库、检索 top-k 丢给模型”的流水线，上线后却发现答非所问、胡编乱造。问题往往不在模型本身，而在四个环节：分块、召回、重排、答案接地。下面按我踩过的坑逐一拆解。

## 分块：切断了语义，也切断了答案

固定长度切分（比如 512 token）最省事，但会把一个完整的定义、一张表格、一段代码拦腰截断。检索时命中了前半段，答案却在后半段，模型只能靠“猜”。

更糟的是跨块指代：块 A 说“该方法在 2023 年提出”，块 B 说“它比基线快 2 倍”，单独看块 B，“它”指什么完全丢失。

我的经验是：
- 优先按结构切分（标题、段落、列表项），再在结构内做长度约束；
- 对表格和代码，保留表头/函数签名作为块的前缀；
- 块之间保留 10%–20% 重叠，但重叠会放大索引体积和重复召回，需要权衡；
- 给每个块加上来源元数据（文档标题、章节路径、页码），检索时一并返回，方便模型引用和人工排查。

一个容易被忽略的点：块大小要和 embedding 模型的训练分布匹配。很多模型在 256–512 token 上表现最好，硬塞 1024 token 的块，向量会“平均化”，语义变得模糊。

## 召回：top-k 不是越大越好

召回失败有两种：该召回的没召回（漏召），不该召回的混进来（噪声）。

漏召常见原因：
- 查询和文档用词不一致（“心梗” vs “心肌梗死”），纯向量检索对术语变体不敏感；
- 多跳问题需要组合多个块的信息，单次检索覆盖不到；
- 长尾实体在 embedding 空间里挤在一起，区分度低。

对策是混合检索：BM25 保关键词精确匹配，向量检索保语义泛化，用 RRF（倒数排名融合）合并。RRF 不需要调分数权重，对异构检索器很友好。

top-k 增大能提升召回率，但会引入噪声，且挤占上下文窗口。我的做法是：先粗召回 50–100 条，再用重排模型压到 5–10 条。直接拿 50 条喂给生成模型，不仅贵，还会让模型在无关信息里“迷失”。

## 重排：被低估的性价比环节

重排（cross-encoder）对 query 和每个候选块做联合编码，精度远高于双塔向量检索，但计算量随候选数线性增长。工程上通常只对前 50–100 条重排，延迟增加几十到几百毫秒，换来的召回质量提升往往比换更大的生成模型更明显。

重排也有失败模式：
- 领域不匹配：通用重排模型对医学术语、代码片段的排序可能不如 BM25；
- 块太长时 cross-encoder 会截断，关键信息在尾部就丢了；
- 重排分数阈值难定，太低放噪声，太高漏召回。

我一般会保留重排前后的 top-k 对比日志，观察“重排把正确答案从第 8 位提到第 1 位”的比例，这是判断重排是否值得上线的最直接指标。

## 答案接地：模型不引用，就等于没检索

即使检索到了正确块，模型仍可能：
- 忽略检索内容，凭参数记忆作答；
- 把多个块的信息缝合出原文没有的结论；
- 引用错误来源（张冠李戴）。

接地（grounding）要在 prompt 和输出结构上同时约束：
- 明确要求“仅根据以下片段回答，片段中没有就说不知道”；
- 要求每个结论后附来源编号，便于程序校验引用是否真实存在；
- 对关键数字、实体做后校验：把答案中的数字与检索块做字符串/数值比对，不一致就降级或人工复核。

但 prompt 约束不是万能的。模型在检索内容与自身知识冲突时，仍可能偏向“自信的错误”。我的做法是加一道轻量校验：用一个小模型判断“答案是否被检索片段支持”（NLI 式二分类），不通过就触发重试或拒答。这会增加延迟，但对高风险场景值得。

## 评估：别只看最终答案

端到端评估（人工打分或 LLM-as-judge）成本高、噪声大。更实用的是分环节指标：
- 分块：块内答案完整率（人工抽检 100 条）；
- 召回：Recall@k、MRR，用标注好的 query-块对；
- 重排：NDCG@k；
- 接地：引用准确率、无支撑断言比例。

没有标注数据时，可以先构造合成 query：从块中反向生成问题，再检验能否召回原块。这能快速暴露分块和召回的硬伤。

## 最后

RAG 的失败很少是单点问题，而是四个环节的误差累积：分块切断了语义，召回漏掉关键块，重排没把正确块顶上来，生成模型又自由发挥。定位问题时，我会先把检索到的块和最终答案并排打印出来，逐条问：答案里的每个事实，能在哪个块里找到？找不到的，就是接地失败；找得到但没召回，就是召回失败；召回了但被截断，就是分块失败。这个笨办法比任何指标都直接。

至于用多大的模型做重排、校验环节要不要上，我还没有在低延迟边缘场景里做过系统对比，这是接下来想补的功课。
