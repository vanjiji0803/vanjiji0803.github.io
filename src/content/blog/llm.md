很多人把「模型能调工具」等同于「Agent 有自主性」。实际跑过生产系统就会知道，`tool_calls` 只是协议层的一次结构化输出，离可靠执行还差一整套工程。

## 工具调用只是协议，不是决策

OpenAI 的 function calling 本质是让模型输出一个 JSON：函数名 + 参数。模型并不「知道」工具是否成功，也不维护跨轮次的副作用状态。它只是在当前上下文里做一次模式匹配。

一个常见失败模式：模型连续两次调用同一个 `search` 工具，参数几乎一样，因为它没意识到第一次已经返回了结果。或者参数里塞了不存在的字段，比如给 `get_weather` 传了 `unit: "celsius"` 但 schema 只接受 `metric`。这些不是模型「笨」，而是协议层没有约束。

所以第一步是把「调用」和「执行」分开：模型只负责提议（proposal），执行器负责校验、执行、记录。

## 用状态机约束循环

裸 `while` 循环加 `max_iterations` 是最脆弱的。我倾向于显式状态机：

- `PLAN`：模型输出下一步动作（调用工具 / 回答 / 请求澄清）
- `VALIDATE`：schema 校验 + 业务规则（比如参数范围、权限）
- `EXECUTE`：真正调用工具，带超时和重试
- `OBSERVE`：把结果（或错误）压缩后写回上下文
- `DECIDE`：判断是否终止（成功、失败、超预算）

每个状态转移都有明确条件，而不是让模型自由发挥。比如 `VALIDATE` 失败时，不直接把错误抛回给模型让它重试，而是先做一次确定性修复（补默认值、纠正枚举），只有修复不了才让模型重新生成。这能显著减少无意义的 token 消耗。

## 上下文预算与结果压缩

工具返回的结果往往比模型需要的多。一个 `search` 返回 10 条文档、每条 500 字，直接塞进上下文就是 5000 token。如果循环 5 次，上下文就爆了。

我的做法是：

1. 工具层做截断，只返回 top-k 和必要字段；
2. `OBSERVE` 阶段用一个小模型或规则做摘要，保留实体、ID、关键数值；
3. 维护一个「工作记忆」结构，只把当前步骤需要的片段注入 prompt，而不是全量历史。

这本质上是把 RAG 的思路用在 Agent 的短期记忆上：检索的不是外部文档，而是本轨迹内已经产生的观察。

## 错误处理：区分可重试与不可重试

工具失败分三类：

- 瞬时错误（超时、限流）：指数退避重试，最多 2 次；
- 参数错误：不重试，走 `VALIDATE` 修复或让模型重新生成；
- 业务错误（无权限、资源不存在）：终止当前分支，把结构化错误写回，让模型决定是否换路径。

关键是把错误也当成一种观察，而不是异常。模型需要看到 `{"error": "permission_denied", "resource": "patient_123"}` 才能做出合理决策。直接抛异常中断循环，等于剥夺了模型的纠错机会。

## 可观测性：没有 trace 就没有 Agent

每次循环至少记录：步骤序号、状态转移、模型输入摘要、工具名与参数、耗时、token 数、结果摘要。这些数据用来回答几个问题：

- 哪一步消耗 token 最多？
- 重试集中在哪个工具？
- 模型是否在重复调用同一工具？

我见过一个案例：Agent 在 `search` 和 `read` 之间来回跳转 8 次，因为 `read` 返回的文档 ID 和 `search` 的 ID 格式不一致，模型一直匹配不上。没有 trace 根本发现不了。

## 评估：别只看最终答案

端到端准确率会掩盖循环本身的问题。我倾向于分层评估：

- 工具选择准确率：给定状态，模型是否选了正确的工具？
- 参数正确率：生成的参数是否通过 schema 和业务校验？
- 步骤效率：完成任务的平均步数，对比人类基线；
- 恢复率：注入工具错误后，Agent 能否在 N 步内恢复。

这些指标可以离线构造，用固定轨迹做回归测试。

## 还没解决的问题

多工具并行调用时的状态一致性我还没想清楚：两个工具同时修改同一资源，观察顺序如何影响模型决策？目前我倾向于串行化有副作用的调用，但这会牺牲延迟。另一个开放问题是：当模型反复失败时，是继续重试、换模型，还是升级到人工？这个阈值目前靠经验设定，缺乏理论依据。

工具调用是能力，执行循环才是工程。把后者做扎实，Agent 才配叫「自主」。
