在构建 LLM 应用时，延迟往往是决定用户体验的关键因素。但「延迟」本身是一个笼统的概念，需要拆解为可度量的指标：首 token 时间（TTFT）、每 token 输出时间（TPOT）、端到端延迟（E2E）。不同的应用场景对这些指标的敏感度不同。例如，聊天机器人更关注 TTFT，因为用户希望立即看到响应开始；而批处理摘要任务则更关注总吞吐量。

**延迟的构成**

一次 LLM 调用的延迟可以分解为：网络传输、排队等待、prefill 阶段（处理输入）、decode 阶段（生成输出）。对于自回归模型，decode 阶段是逐 token 进行的，因此输出长度直接决定了解码时间。假设模型在 A100 上的 TPOT 为 20ms，那么生成 500 个 token 就需要 10 秒。这还不包括 prefill 时间，prefill 时间与输入长度成正比，且通常比 decode 快得多，但在长上下文场景下也不可忽略。

**流式输出**

流式输出通过将生成的 token 逐步返回给客户端，显著改善感知延迟。用户不必等待完整响应，TTFT 可以降到几百毫秒。但流式也带来复杂性：需要处理 SSE 或 WebSocket 连接、错误重试、以及部分响应可能不完整的问题。另外，流式并不减少总计算时间，只是改变了延迟的分布。在实现时，要注意缓冲区大小和 flush 策略，避免因 Nagle 算法导致的小包延迟。

**缓存策略**

缓存是降低延迟最直接的手段，但需要区分几种类型：

1. **精确缓存**：对相同的输入（prompt + 参数）直接返回缓存结果。适用于 FAQ、模板化查询。命中率取决于查询的重复率。实现时可以用 Redis 或内存缓存，键为 prompt 的哈希。

2. **语义缓存**：对语义相似的查询返回缓存结果。通常用 embedding 计算相似度，设定阈值（如 0.95）。风险是可能返回不准确的答案，需要谨慎设置阈值，并加入人工审核或 fallback。

3. **KV 缓存**：在推理层面，缓存注意力机制的 key/value 对，避免重复计算。对于多轮对话，如果前缀相同，可以复用 KV 缓存。vLLM 的 PagedAttention 和 prefix caching 就是典型实现。但 KV 缓存占用显存，需要权衡。

**批处理**

批处理通过将多个请求合并成一个批次，提高 GPU 利用率，从而提升吞吐量。但批处理会增加单个请求的延迟，因为要等待批次填满或超时。常见的策略是动态批处理（continuous batching），如 vLLM 和 TensorRT-LLM 所采用的，它允许在 decode 阶段动态加入新请求，减少等待时间。对于在线服务，需要设置最大批次大小和超时时间，在延迟和吞吐之间找到平衡。

**模型路由**

模型路由根据请求的复杂度或延迟要求，将请求分发给不同规模的模型。例如，简单查询用 7B 模型，复杂推理用 70B 模型。路由可以基于规则（如输入长度、关键词）或学习到的分类器。难点在于准确判断请求的难度，以及维护多个模型的部署成本。另一种路由是混合专家（MoE），在模型内部进行路由，但那是训练层面的。

**延迟预算的分配**

假设我们有一个端到端延迟预算为 2 秒的对话应用，可以这样分配：网络传输 100ms，排队 50ms，prefill 200ms，decode 1.5s（约 75 个 token，TPOT 20ms），剩余 150ms 作为缓冲。如果输出更长，就需要调整预算或优化模型。

**监控与优化**

在生产环境中，需要监控 P50、P90、P99 延迟，以及 TTFT 和 TPOT。使用分布式追踪（如 OpenTelemetry）记录每个阶段的耗时。优化手段包括：量化（FP16/INT8）、使用更快的推理引擎（TensorRT-LLM、vLLM）、调整 batch size、启用连续批处理、以及使用投机解码（speculative decoding）来加速 decode。

**未解决的问题**

如何动态调整路由策略以适应负载变化？语义缓存的阈值如何自动优化？这些仍然是我在探索的问题。延迟优化没有银弹，需要根据具体场景权衡。

总之，理解延迟的构成，并合理运用流式、缓存、批处理和路由，才能构建出既快又稳的 LLM 应用。
