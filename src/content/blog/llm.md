在部署 LLM 应用时，延迟往往是用户体验的第一道门槛。但「延迟」本身是个笼统的概念：用户感知的延迟、端到端延迟、首 token 延迟（TTFT）和生成延迟（TPOT）需要分开度量。如果不先拆解延迟预算，优化就容易变成盲目的调参。

## 延迟的构成

一次典型的 LLM 请求包含以下阶段：网络传输、排队、预处理（tokenization、模板拼接）、推理（prefill + decode）、后处理（解析、过滤）。对于流式响应，TTFT 主要由排队 + prefill 决定，而 TPOT 由 decode 阶段决定。假设模型在 A100 上以 50 tokens/s 生成，输出 500 tokens 就需要 10 秒——这还没算上网络和排队。因此，设定预算时，先明确 SLO：例如 TTFT < 1s，TPOT < 50ms，端到端 < 5s。

## 流式输出：改善感知延迟

流式（streaming）不减少总生成时间，但能大幅降低感知延迟。用户看到第一个 token 后，等待焦虑会下降。实现上，SSE 比 WebSocket 更简单，但要注意代理缓冲：Nginx 默认会缓冲响应，需要设置 `proxy_buffering off` 或使用 `X-Accel-Buffering: no`。另外，流式下错误处理更复杂——如果生成中途失败，已经输出的内容无法撤回，通常需要在客户端设计重试或拼接逻辑。

## 缓存：命中率与一致性

缓存分为精确匹配和语义缓存。精确缓存（如 Redis）实现简单，但命中率低，尤其对开放式生成。语义缓存（用 embedding 相似度匹配）能提高命中率，但需要设置阈值（如 cosine > 0.95），并承担误命中风险。工程上，我倾向于对高频、确定性强的查询（如 FAQ）使用精确缓存，对生成类请求慎用语义缓存，除非有明确的评估集验证误命中率可接受。

另一个维度是 KV 缓存复用。对于多轮对话，如果前缀相同，可以复用 KV 缓存，减少 prefill 计算。vLLM 的 PagedAttention 和 prefix caching 能自动处理部分场景，但需要确保请求的路由一致（同一会话打到同一实例）。

## 批处理：吞吐与延迟的权衡

连续批处理（continuous batching）能提高 GPU 利用率，但会增加单个请求的排队延迟。在流量波动大的场景，可以设置最大批大小和最大等待时间（如 50ms），在吞吐和延迟间折中。对于离线任务（如批量摘要），可以接受更高的延迟，用更大的批处理提升吞吐。

## 模型路由：按需分配

模型路由根据请求的复杂度选择不同规模的模型。例如，简单分类或抽取任务用小模型（7B），复杂推理用大模型（70B）。路由策略可以基于规则（如输入长度、关键词）或学习一个轻量分类器。难点在于评估路由准确性：错误路由会导致质量下降。建议先用离线评估集确定各模型的能力边界，再上线 A/B 测试。

## 监控与迭代

延迟优化不是一劳永逸的。需要监控 P50/P95/P99 延迟、TTFT、TPOT、缓存命中率、路由分布等指标。OpenTelemetry 可以追踪请求链路，但注意采样率避免开销。

最后，延迟预算需要与产品目标对齐。不是所有场景都需要极致低延迟——后台任务可以放宽，交互式应用则需严格。我目前还在探索如何动态调整预算（如根据用户付费等级），这涉及资源隔离和优先级调度，尚未有成熟方案。
