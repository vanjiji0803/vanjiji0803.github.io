在构建 LLM 应用时，延迟往往是用户体验的第一道门槛。但「延迟」本身是一个笼统的概念，需要拆解为可度量的阶段，才能针对性地优化。本文将讨论延迟预算的制定，以及流式、缓存、批处理和模型路由这四种常见手段的机制、权衡与失效模式。

## 延迟的构成

一次典型的 LLM 请求包含以下阶段：网络传输、排队、预处理（如 tokenization、检索）、推理（prefill 和 decode）、后处理（如解析、过滤）。每个阶段都有其延迟特征。例如，prefill 阶段与输入长度强相关，而 decode 阶段与输出长度线性相关。制定预算时，需要明确每个阶段的 P50 和 P95 目标，而不是一个笼统的「端到端 2 秒」。

一个实用的方法是：先确定用户可接受的端到端时间（例如 3 秒），再根据业务逻辑分配各阶段预算。例如，检索增强生成（RAG）中，检索可能占 200-500 毫秒，prefill 占 300 毫秒，decode 占 1.5 秒（假设输出 300 token，吞吐 200 token/s）。剩余时间留给网络和后处理。

## 流式输出：感知延迟的优化

流式输出（streaming）并不减少总生成时间，但能显著降低「首 token 时间」（TTFT），从而改善感知延迟。实现上，通常使用 Server-Sent Events（SSE）或 WebSocket 逐块返回 token。需要注意的是，流式输出会引入新的复杂性：前端需要处理不完整的句子、错误恢复、以及取消请求。

一个常见的陷阱是：在流式过程中进行内容过滤或结构化解析。如果过滤逻辑需要完整上下文，则流式输出与安全要求可能冲突。此时可以考虑分块过滤，或仅在流结束后进行最终校验。

## 缓存：命中率与一致性的权衡

缓存是降低延迟最直接的手段，但 LLM 应用的缓存有其特殊性。常见的缓存层级包括：

- **精确匹配缓存**：对相同的 prompt 返回相同结果。适用于确定性高的场景，如 FAQ。但 LLM 的输出具有随机性（temperature > 0），缓存可能返回与当前期望不一致的结果。
- **语义缓存**：通过 embedding 相似度匹配历史请求。需要设置相似度阈值，并处理误匹配。阈值过高则命中率低，过低则可能返回不相关答案。
- **KV 缓存复用**：在推理层面，对相同前缀的请求复用 KV 缓存（如 vLLM 的 prefix caching）。这需要请求具有相同的前缀，对多轮对话或系统提示固定的场景有效。

缓存的关键指标是命中率和错误率。需要监控缓存返回的结果是否被用户接受（例如通过点赞/点踩），以评估缓存质量。

## 批处理：吞吐与延迟的平衡

批处理（batching）是提高 GPU 利用率的常用手段，但会引入排队延迟。连续批处理（continuous batching）允许在批次中动态加入新请求，减少了等待时间。然而，批大小越大，单个请求的延迟可能越高，因为计算资源被分摊。

在实际部署中，需要根据 SLA 调整批处理策略。例如，对延迟敏感的请求可以设置较小的最大批大小，或使用优先级队列。一个常见的做法是：将请求分为交互式（低延迟）和后台式（高吞吐），分别路由到不同的推理实例。

## 模型路由：按需分配算力

模型路由（model routing）根据请求的复杂度或类型，将其分配给不同规模的模型。例如，简单查询路由到小模型（如 7B），复杂推理路由到大模型（如 70B）。这能显著降低平均延迟和成本。

路由策略可以基于：

- **规则**：根据关键词或请求长度。
- **分类器**：训练一个轻量级模型预测请求难度。
- **置信度**：先让小模型生成，若置信度低再升级到大模型。

路由的挑战在于准确性和一致性。错误的路由可能导致质量下降。需要建立评估集，定期检查路由决策的准确性。

## 监控与迭代

延迟优化不是一劳永逸的。需要建立端到端的监控，包括各阶段延迟、缓存命中率、路由分布等。同时，要关注长尾延迟（P99），因为用户对卡顿的感知往往来自长尾。

最后，延迟预算的制定需要结合业务场景。对于实时交互，TTFT 可能比总生成时间更重要；对于后台任务，吞吐量可能是首要目标。没有通用的最优解，只有针对具体场景的权衡。
