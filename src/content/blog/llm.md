最近在做一个手术室的RAG智能体（Surg-Agent），我越来越意识到一个常被混淆的概念：工具调用（tool calling）不等于智能体（agent）。很多demo里，模型能调函数、查数据库、返回结果，看起来挺智能，但真正落地到生产环境，你会发现它只是“有工具的函数封装”，离“智能体”还差一个关键部分——**可靠的执行循环**。

## 工具调用 vs. 智能体

工具调用是模型输出一个结构化指令（比如`search_document(query)`），然后由代码去执行。而智能体是模型在一个循环中自主决定下一步动作：观察结果、调整计划、再次调用工具，直到任务完成。这个循环的可靠性，决定了智能体能不能真正用起来。

我见过不少团队把工具调用包装成“智能体”，但循环是硬编码的：用户问一句，调一次工具，返回结果，结束。这更像是RAG的变体，不是智能体。真正的智能体要能处理多步任务，比如：

> “帮我找最近的手术视频，分析其中的出血阶段，并总结关键操作。”

这需要检索、时序定位、摘要等多个步骤，而且步骤之间可能有依赖。如果循环设计不好，模型可能在一个工具结果上反复打转，或者漏掉必要的步骤。

## 执行循环的核心设计

我目前实践下来，一个可靠的执行循环至少包含四个部分：

1. **状态管理**：每一步的输入、输出、中间结果都要有明确的存储。我常用一个`AgentState`字典，包含`task`, `history`, `current_step`, `tool_results`等。这样模型可以随时查看历史，避免重复调用。
2. **循环终止条件**：必须定义什么时候停止。常见的有：模型输出`final_answer`、达到最大步数（比如10步）、或者超时。我倾向于设置最大步数，因为模型有时候会陷入死循环。
3. **错误处理**：工具调用可能失败（网络超时、参数错误）。循环里要捕获异常，把错误信息反馈给模型，让它决定是重试还是换一种方式。
4. **上下文裁剪**：每次循环都会增加token消耗。当历史过长时，需要裁剪或摘要。我通常保留最近的几轮，把更早的对话摘要成一段。

## 一个具体的例子

在Surg-Agent里，我们有一个工具`analyze_surgical_video(video_path, query)`，它调用一个YOLO检测模型识别手术器械，并返回检测结果。循环逻辑大致如下：

```python
for step in range(max_steps):
    response = llm.chat(messages, tools=[search_video, analyze_surgical_video, ...])
    if response.finish_reason == "stop":
        return response.content
    for tool_call in response.tool_calls:
        try:
            result = execute_tool(tool_call)
            messages.append({"role": "tool", "content": json.dumps(result)})
        except Exception as e:
            messages.append({"role": "tool", "content": f"Error: {e}"})
```

这里有个坑：如果工具返回的结果很大（比如检测框的坐标），直接塞进上下文会爆炸。我们会在工具内部做后处理，只返回摘要信息，比如“检测到3个器械，置信度分别为0.9, 0.8, 0.7”。这样既保留了关键信息，又控制了token。

## 失败模式与对策

我踩过不少坑，总结几个常见的失败模式：

- **模型不按指令调用工具**：有时候模型会直接输出答案而不调用工具，即使任务需要检索。对策是强化系统提示，明确“你必须使用工具获取信息”，或者用few-shot示例。
- **工具参数错误**：模型生成的参数可能不符合工具schema。比如日期格式不对。我通常会在工具执行前做参数校验，并返回具体的错误信息，让模型自己修正。
- **循环不收敛**：模型可能反复调用同一个工具，或者在不同工具间跳来跳去。对策是设置“重复调用惩罚”：如果模型在最近N步内调用了同一个工具，就在提示中提醒它“你已经调用过该工具，请基于已有结果继续”。
- **幻觉在循环中放大**：模型可能基于错误的中间结果继续推理。我倾向于在每一步都要求模型输出“当前置信度”或“是否需要用户确认”，但这样会增加延迟，需要权衡。

## 评估执行循环

评估智能体比评估单个模型更难。我目前的做法是：

1. **单元测试**：针对每个工具，测试给定输入是否返回预期结果。
2. **端到端测试**：准备一组任务，比如“回答某个问题需要检索+推理”，看智能体能否在指定步数内完成。
3. **轨迹分析**：记录每一步的调用和中间结果，人工检查是否有重复、错误或逻辑跳跃。

我还在尝试用“成功率”和“平均步数”作为指标，但说实话，任务定义很难统一，目前还是以人工评估为主。

## 未解的问题

我还没完全解决的一个问题是：**如何让循环自适应地调整策略**？比如，当任务简单时，模型应该少调用工具；当任务复杂时，应该多探索。现在都是固定最大步数，有时候简单任务浪费了很多步。也许可以用强化学习，但工程上还不成熟。

另一个问题是**多智能体协作**：如果多个智能体共享工具，如何避免资源竞争？我还没试过，但感觉状态管理会更复杂。

总之，工具调用只是起点，真正的智能体需要精心设计的执行循环。希望我的经验能给你一些启发。如果你有更好的做法，欢迎交流。
