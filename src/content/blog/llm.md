很多团队在 demo 里让模型调用一两个工具，就宣称自己有了 agent。但工具调用只是能力，不是自主性。真正的代理需要一套可靠的执行循环，来处理规划、状态、错误和上下文。下面是我在构建手术代理 Surg-Agent 时总结的几个关键点。

## 1. 用状态机约束循环，而不是让模型自由发挥

模型生成工具调用很容易，难的是知道何时停止、何时重试、何时升级。我的做法是显式定义状态机：`IDLE -> PLANNING -> EXECUTING -> OBSERVING -> (REPLANNING | DONE | FAILED)`。每个状态有明确的退出条件，比如 EXECUTING 必须收到工具结果或超时；OBSERVING 后如果连续两次工具调用返回相同错误，就进入 FAILED 并触发人工兜底。模型只负责在 PLANNING 和 REPLANNING 时生成下一步动作，不控制状态迁移。这样即使模型输出格式错误，循环也不会卡死。

## 2. 工具调用的错误处理要分类型

工具失败大致分三类：瞬时错误（网络超时）、参数错误（模型传了不存在的枚举值）、语义错误（工具执行成功但结果不符合预期）。对瞬时错误，指数退避重试 2 次；对参数错误，把错误信息作为 observation 返回给模型，让它重新生成参数，但限制最多 3 次；对语义错误，比如检索到的文档为空，不要重试，而是触发 replanning，换一个工具或换查询。关键是把错误信息结构化，比如 `{"error_type": "invalid_argument", "message": "...", "retryable": false}`，模型才能正确决策。

## 3. 上下文预算：工具结果要截断和摘要

每次工具调用的结果都会进入上下文。一个检索工具返回 10 个 chunk，每个 500 token，几次调用就撑爆 8k 窗口。我的策略是：工具结果先经过一个轻量摘要器（可以用小模型或规则），只保留与当前子目标相关的字段，并且限制总 token 不超过预算的 30%。对于长文档，只保留首尾和匹配片段。另外，历史 observation 要定期压缩，比如每 5 轮把旧结果合并成一句状态摘要。否则模型会迷失在细节里。

## 4. 评估要覆盖循环层面，而不只是单步准确率

单步工具调用准确率 90% 听起来不错，但 5 步循环的成功率可能只有 0.9^5 ≈ 59%。所以评估必须看端到端任务成功率、平均步数、错误恢复率。我构造了一个小型测试集，包含 50 个多步任务，每个任务有明确的成功条件（比如最终答案包含特定实体）。同时记录每步的延迟和 token 消耗，用来定位瓶颈。另一个重要指标是“无效循环率”：模型在相同状态间来回切换的次数。超过阈值就说明规划有问题。

## 5. 可观测性：记录完整轨迹

没有轨迹就无法调试。每次循环要记录：状态迁移、模型输入输出、工具调用参数和结果、耗时、token 数。我简单用 JSONL 落盘，配合一个可视化脚本回放。曾经遇到一个 bug：模型在 REPLANNING 时反复调用同一个搜索工具，因为错误信息里没有包含“已尝试过”的提示。加上历史动作摘要后解决。

## 6. 模型选择：不是越大越好

在循环里，模型需要稳定遵循格式、理解错误信息、做简单规划。我对比过几个模型，发现小模型在格式遵循上更容易出错，但大模型在长上下文里反而容易忽略早期指令。目前我的做法是：规划用较大模型（如 GPT-4 级别），工具参数生成用较小模型（如 7B 微调后），摘要用规则或小模型。这样平衡了成本和可靠性。
