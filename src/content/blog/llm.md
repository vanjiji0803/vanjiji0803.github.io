在构建 LLM 应用时，延迟往往比吞吐更影响用户体验。一个常见的误区是只关注平均响应时间，而忽略了首 token 延迟（TTFT）和 token 间延迟（TBT）。对于交互式应用，TTFT 决定了用户感知的“开始响应”速度，TBT 则影响阅读流畅度。通常，TTFT 应控制在 500ms 以内，TBT 低于 50ms 才能让用户感觉自然。但端到端延迟预算需要根据场景分配：例如，一个 RAG 问答系统可能将 200ms 分配给检索，300ms 给模型推理，剩余 100ms 给网络和后处理。

流式输出是降低感知延迟最直接的手段。通过 SSE 或 WebSocket 逐 token 返回，用户可以在模型生成完整答案前开始阅读。但流式并非没有代价：它增加了客户端状态管理的复杂性，且在某些场景下（如需要完整 JSON 输出）无法使用。我的经验是，对于聊天和长文本生成，流式是必须的；对于结构化输出，可以先用流式返回部分字段，但最终仍需等待完整响应。

缓存是另一个关键杠杆。精确缓存（如 Redis 存储 prompt 哈希）对重复查询有效，但 LLM 的输入往往有细微变化。语义缓存通过嵌入向量相似度匹配，能覆盖更多情况，但需要权衡误匹配风险。例如，阈值设为 0.95 时，可能将“如何重置密码”和“怎样修改密码”视为相同，导致错误回答。我通常建议在缓存层加入业务规则过滤，并监控缓存命中率和错误率。

批处理能提升吞吐，但可能增加延迟。连续批处理（continuous batching）在推理服务器中动态合并请求，显著提高 GPU 利用率，但会引入排队延迟。对于延迟敏感的应用，可以设置最大批大小和超时时间，例如等待 10ms 或凑齐 8 个请求就立即执行。在 vLLM 或 TensorRT-LLM 中，这些参数需要根据实际负载调整。

模型路由是平衡延迟与质量的策略。简单查询用小模型（如 7B），复杂查询用大模型（如 70B）。路由决策可以基于查询长度、关键词或轻量分类器。但路由本身有开销，且小模型可能失败，需要回退机制。我曾在手术 Agent 中尝试基于规则的路由：如果查询包含“解剖结构”或“并发症”，则路由到较大模型；否则使用小模型。这降低了平均延迟，但增加了系统复杂性。

最后，延迟优化需要可观测性。记录每个阶段的耗时（检索、推理、后处理），并设置告警。没有度量，就无法优化。你可以在日志中埋点，或使用 OpenTelemetry 跟踪。记住，延迟预算不是固定值，而是随着业务需求演进的动态目标。
