很多人把 LLM 的解码当成一个黑盒：调一下 temperature 就完事。但解码本质是在概率空间里做搜索，不同策略直接决定输出的稳定性、多样性和延迟。这篇文章拆开讲。

## 解码的基本问题

给定上下文，模型输出词表上的概率分布 P(y_t | y_<t, x)。解码就是从这个分布里选 token 序列。贪心解码每步取 argmax，简单但容易陷入重复；beam search 维护 k 条候选路径，每步扩展并保留得分最高的 k 条。

beam search 的得分通常是 log 概率之和，这有个已知问题：长序列得分更低，导致偏好短输出。常见修正是长度归一化（除以长度^α）。但即使修正，beam search 在开放生成里也常输出“安全但平庸”的文本，因为高概率路径往往是最保守的。

## 采样：用随机性换多样性

采样按概率抽 token。纯随机采样会抽到长尾里的垃圾 token，所以需要截断：

- **top-k**：只保留概率最高的 k 个 token。k 固定，但分布形状变化时不够灵活。
- **top-p（nucleus）**：保留累计概率达到 p 的最小集合。分布尖锐时集合小，平坦时集合大，更自适应。
- **temperature**：对 logits 除以 T 再 softmax。T<1 让分布更尖，T>1 更平。注意 temperature 和 top-p 会相互作用：高温下 top-p 的候选集会被撑大。

工程上常见组合是 temperature 0.7 + top-p 0.9，但这不是金科玉律。代码生成通常要低温甚至贪心，创意写作可以高温。

## 失败模式

1. **重复循环**：贪心或低温采样容易在“的的的”或整句复读。 repetition penalty 能缓解，但会误伤正常重复（如列表项）。
2. **截断导致的语义断裂**：top-p 太小会把合理但概率稍低的 token 砍掉，输出变得机械。
3. **beam search 的暴露偏差**：训练时用 teacher forcing，推理时 beam 搜索的路径可能不在训练分布内，导致评分不可靠。
4. **温度与校准**：模型 logits 未必校准，temperature 不是“置信度调节器”，别指望 T=0.5 就代表 50% 确定性。

## 结构化输出与约束解码

当需要 JSON 或函数调用时，自由采样会破坏格式。约束解码在每步把不符合语法的 token 概率置零（或 mask），再归一化。实现上可以用有限状态机或语法解析器维护合法 token 集合。代价是每步多一次 mask 计算，且可能扭曲分布——如果合法集合概率质量很低，输出会变得不自然。

## 评估与观测

解码参数没有万能值，要靠评估闭环：

- 离线：用 pass@k、BLEU/ROUGE、或任务特定指标扫参数网格。
- 在线：记录每次请求的 temperature、top-p、输出长度、重复率、格式错误率。
- A/B：固定模型和 prompt，只调解码参数，看业务指标。

我还没在生产环境大规模验证过“动态温度”——根据上下文熵自动调 T。直觉上可行，但需要小心反馈回路。

## 小结

解码不是调参玄学，而是搜索策略的取舍：beam search 求稳，采样求活，约束解码求准。理解每步的概率操作，才能在上线时知道该动哪个旋钮。
