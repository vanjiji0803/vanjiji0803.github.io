解码（decoding）常被当成一个 `temperature=0.7` 的参数问题，但在实际系统里，它决定了输出分布、延迟、可复现性和幻觉率。这篇文章从算法机制出发，聊清楚 beam search、采样、温度各自的适用边界，以及我在工程中踩过的坑。

## 1. 解码的本质：在概率空间里做搜索

自回归模型每一步输出一个 logits 向量，softmax 后得到词表上的概率分布。解码策略就是在这个分布上选择下一个 token 的规则。

- **贪心（greedy）**：每步取 argmax。复杂度 O(n)，但容易陷入重复循环，且对局部最优敏感。
- **Beam search**：维护 k 条候选序列，每步扩展并保留总分最高的 k 条。复杂度 O(k·n·V)，V 是词表大小。
- **采样（sampling）**：按概率分布随机抽取。引入随机性，但可能抽到低概率的坏 token。
- **Top-k / Top-p（nucleus）**：先截断分布再采样，控制随机性的范围。

关键点：beam search 优化的是序列联合概率，而人类对话的“好”往往不等于概率最高。这就是为什么开放生成用 beam search 会显得平淡、保守，甚至答非所问。

## 2. Beam search 的适用场景与陷阱

Beam search 在**输出空间受限、有明确正确答案**的任务上表现好：机器翻译、语音识别、结构化抽取（如 JSON 生成）。因为这些任务里，高概率序列通常就是正确序列。

但有几个工程陷阱：

1. **长度偏差**：联合概率随长度递减，beam search 倾向短输出。需要长度归一化（length penalty），但 penalty 系数很难调，过大又会产生冗长重复。
2. **多样性坍塌**：k 条 beam 往往只差一两个 token，实际多样性远低于 k。
3. **延迟**：k 倍计算量。在边缘设备上，k=4 可能直接让首 token 延迟翻倍。

我在手术视觉 agent 里做过一个对比：结构化报告生成用 beam search（k=3）确实比采样稳定，但一旦 prompt 里加入自由文本描述，beam 的输出就变得机械。最后改成“结构化字段用 beam，自由描述用低温采样”的混合策略。

## 3. 温度、top-k、top-p 的机制

温度 T 作用于 logits：`p_i = softmax(z_i / T)`。

- T < 1：分布更尖锐，高概率 token 被放大，输出更确定。
- T > 1：分布更平坦，低概率 token 有机会被选中，创造性增强但风险上升。
- T → 0：退化为贪心。

Top-k 保留概率最高的 k 个 token 再归一化；top-p 保留累积概率达到 p 的最小集合。两者区别在于：top-k 的候选数固定，top-p 随分布形状自适应。当模型很确定时，top-p 集合很小；当模型犹豫时，集合变大。

实践上，**top-p 通常比 top-k 更稳**，因为词表分布的长尾在不同上下文下差异很大。我一般用 top-p=0.9~0.95，temperature=0.7 作为对话默认；需要确定性时 temperature=0.1 + top-p=1.0。

## 4. 失败模式

- **重复循环**：低温 + 贪心容易复读。加 repetition penalty 或 frequency penalty 能缓解，但 penalty 过大会破坏语法。
- **截断导致的语法错误**：top-p 太小（如 0.5）会把必要的功能词（the、of）截掉，输出变得破碎。
- **温度与 top-p 耦合**：高温 + 小 top-p 等于把平坦分布强行截断，效果不可预测。调参时最好固定一个、调另一个。
- **不可复现**：采样本身随机。做评测时必须固定 seed，否则 A/B 对比没有意义。

## 5. 评测方法

解码参数没有万能最优，必须用任务指标衡量：

- **确定性任务**（抽取、分类）：用 exact match / F1，比较 greedy、beam、低温采样。
- **开放生成**：用 BLEU/ROUGE 不够，最好加 LLM-as-judge 或人工评分，同时统计重复率、长度分布。
- **在线系统**：监控首 token 延迟、输出长度、重试率。解码参数变化会直接影响这些指标。

一个容易忽略的点：**评测集上的最优温度，往往在真实流量上偏移**。因为评测 prompt 分布和线上不同。我习惯保留一个 shadow 流量，用固定 seed 跑新参数，观察一周再切。

## 6. 工程实现细节

- **批量解码**：不同序列长度不同，beam search 需要 padding 和 mask，显存开销大。vLLM 的 continuous batching 对采样友好，对 beam 支持有限。
- **结构化输出**：JSON 生成可以用 grammar-constrained decoding（如 outlines），把非法 token 的概率置零，比调温度可靠得多。
- **边缘部署**：TensorRT-LLM 支持 top-k/top-p 的 fused kernel，但 beam search 的 kernel 优化较少。在 IGX 上，我优先用采样 + 约束解码，而不是 beam。

## 7. 开放问题

解码策略和 RAG 的交互我还没系统研究：检索到的上下文越长，模型分布越尖锐，此时温度是否应该调低？另外，agent 的多步规划里，每步解码的随机性会累积，是否需要逐步降低温度？这些目前更多靠经验，缺乏理论指导。

总之，解码不是调一个参数，而是在**确定性、多样性、延迟、可复现性**之间做权衡。理解机制，才能在不同任务上做出合理选择。
