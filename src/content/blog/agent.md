在构建 Agent 系统时，意图识别往往是最容易被低估的环节。很多人以为，有了大语言模型（LLM），意图识别就是一句 prompt 的事。但实际落地时，你会发现从用户的一句话到可执行的任务状态，中间隔着巨大的工程鸿沟。

## 意图识别不只是分类

传统意图识别是分类问题：给定 utterance，输出预定义的意图标签。但在 Agent 系统中，意图识别要解决的问题更复杂——它需要同时完成三件事：

1. **意图分类**：用户想做什么？（查天气、订机票、调设备）
2. **槽位填充**：完成这个意图需要哪些参数？（目的地、时间、设备 ID）
3. **状态转换**：当前对话上下文下，这个意图是否合法？是否触发状态机的迁移？

只做分类的 Agent 是“一次性”的，无法处理多轮对话和条件依赖。比如用户说“帮我打开客厅的灯”，如果灯已经开着，意图仍然是“开灯”，但状态机应该拒绝执行或提示用户。

## 两种主流实现路线

### 1. 纯 LLM 分类 + JSON 输出

这是最直接的方式：把用户输入和对话历史塞进 prompt，让 LLM 输出 JSON，包含意图、槽位和置信度。

```json
{
  "intent": "turn_on_light",
  "slots": {"location": "living_room"},
  "confidence": 0.92
}
```

优点：实现快，对长尾意图泛化好。缺点：延迟高（推理 200-500ms），成本高，且输出不稳定——有时会漏槽位，有时会编造不存在的意图。

### 2. 小模型分类 + LLM 槽位填充

用 BERT 或 DistilBERT 做意图分类，用 LLM 做槽位填充。意图分类是 few-shot 或 fine-tune，槽位填充用 LLM 抽取实体。

优点：意图分类延迟低（<50ms），成本低，可离线评估。缺点：需要维护训练数据，新意图上线要重新训练。

我目前倾向于混合方案：高频意图用小模型，长尾和未知意图 fallback 到 LLM。但这样引入了路由逻辑，需要监控两个模型的置信度，避免互相干扰。

## 状态机的必要性

意图识别只解决“用户想做什么”，但 Agent 还需要知道“现在能不能做”。这需要状态机来管理。

例如，一个手术室 Agent（我做过类似项目）的状态可能包括：`IDLE`、`WAITING_CONFIRM`、`EXECUTING`、`PAUSED`。当状态为 `EXECUTING` 时，用户说“暂停”是合法意图，但说“开始”就非法。

状态机的好处是让意图识别有约束，避免 LLM 幻觉。但状态机设计要小心：状态粒度太粗，无法表达复杂流程；太细则状态爆炸。一个折衷是分层状态机，顶层控制对话流程，底层控制具体任务。

## 失败模式与工程对策

### 槽位缺失

用户说“帮我定明早的机票”，但没说目的地。此时意图是 `book_flight`，但槽位 `destination` 缺失。对策：不要直接执行，而是发起澄清对话。LLM 可以生成澄清问题，但最好用模板，避免发散。

### 意图冲突

用户说“打开灯，但别开太亮”，这其实是两个意图：开灯 + 调亮度。单意图分类无法处理，需要支持多意图输出，或者用槽位 `brightness` 表示。

### 置信度校准

LLM 输出的 confidence 并不可靠。我试过让 GPT-4 输出 0-1 的置信度，结果高置信度时也可能错。更好的做法是让模型输出 logits 或使用多个样本投票，但成本高。工程上，我常设一个阈值，低于阈值则进入人工确认流程。

## 评估与监控

意图识别系统上线后，必须持续监控。我建议记录以下指标：

- **意图准确率**：按意图分层的准确率，避免被高频意图掩盖。
- **槽位 F1**：槽位填充的精确率和召回率。
- **状态转换成功率**：在状态机约束下，合法转换的比例。
- **端到端任务成功率**：用户最终目标是否达成，这比单步准确率更重要。

离线评估时，构建一个包含多轮对话的测试集，模拟真实用户的打断、修正和省略。在线监控时，用日志分析用户投诉或重试率。

## 一个未解决的问题

目前我还没找到好的方法来自动发现新意图。当用户说了系统没见过的意图时，我们只能 fallback 到 LLM，但 LLM 可能返回一个模糊的意图，导致后续流程无法执行。我尝试过用 embedding 相似度聚类，但效果一般。也许需要引入主动学习，让系统在低置信度时询问用户，但这样会增加交互成本。

意图识别不是一锤子买卖，它需要和状态机、对话管理、任务执行紧密结合。把意图识别当作一个持续优化的组件，而不是一个模型，可能是更务实的思路。
