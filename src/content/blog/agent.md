在 Agent 系统里，意图识别常被简化成“分类问题”：给用户话语打一个标签，比如 `book_flight`。但真正要驱动执行，标签远远不够。我们需要把自然语言映射成一个**可执行的任务状态**：目标、槽位、约束、优先级、缺失信息、以及下一步动作。这中间隔着一整套工程决策。

## 从标签到状态：为什么分类不够

假设用户说：“帮我订明天下午去上海的航班，靠窗，别太贵。”

一个分类器输出 `book_flight`，但 Agent 需要的是：

```json
{
  "intent": "book_flight",
  "slots": {
    "destination": "上海",
    "date": "2025-06-11",
    "time_window": "afternoon",
    "seat_preference": "window",
    "price_sensitivity": "high"
  },
  "missing": ["origin"],
  "constraints": ["price_sensitivity=high"],
  "status": "awaiting_slot"
}
```

这个结构才是可执行的。它告诉规划器：还缺 `origin`，需要追问；`price_sensitivity` 会影响排序策略；`time_window` 需要解析成具体时间范围。

## 意图 Schema 的设计权衡

Schema 的粒度直接决定系统的灵活性与复杂度。

- **扁平标签**：`intent` 一个字段。实现简单，但无法表达复合意图（“订票并选座”）。
- **层次化**：`domain` + `action` + `sub_action`。例如 `travel.book.flight`。便于路由，但枚举爆炸。
- **槽位填充（slot filling）**：意图 + 参数集合。最接近可执行状态，但需要定义每个槽位的类型、是否必填、默认值。

我的经验是：**从扁平标签起步，但一开始就把槽位设计成独立结构**。因为意图分类的准确率再高，槽位缺失或错误照样让执行失败。

槽位类型要明确：
- `string`：自由文本，如目的地。
- `enum`：有限集合，如舱位等级。
- `datetime`：需要归一化，处理“明天下午”“下周三”等相对表达。
- `number`：带单位，如价格上限。
- `boolean`：如“是否直飞”。

对于 `datetime`，我习惯用规则 + LLM 混合：先尝试正则和日期库，失败再交给模型，并要求输出 ISO 8601。这样能减少模型在简单情况下的幻觉。

## 歧义与多意图：别急着二选一

用户说：“我想退掉上周订的那张票，然后重新订一张。”这是两个意图，且有依赖关系。

处理策略：
1. **拆分**：用句子边界或连接词切分，分别识别。
2. **排序**：按时间或逻辑依赖排序，退票在前，订票在后。
3. **状态机**：每个子任务是一个状态节点，前一个完成才进入下一个。

如果无法确定顺序，不要猜。生成一个澄清问题：“您是想先退票再重新订，还是只退票？”

## 从状态到执行：状态机与规划循环

任务状态不是静态的。它随着对话和工具调用而迁移。一个简化的状态机：

- `idle` → 收到话语 → `parsing`
- `parsing` → 成功 → `ready`；缺槽位 → `awaiting_slot`
- `awaiting_slot` → 用户补充 → `parsing`
- `ready` → 规划器生成动作序列 → `executing`
- `executing` → 工具返回 → `completed` 或 `failed`
- `failed` → 可重试 → `executing`；不可重试 → `aborted`

关键点：**意图识别不是一次性动作**。用户补充信息时，需要增量更新状态，而不是重新解析整个话语。这要求解析器支持“合并”语义：新槽位覆盖旧槽位，冲突时标记 `conflict` 并追问。

## 评估：别只看意图准确率

意图识别的评估应该分层：

- **意图分类**：准确率、混淆矩阵。但注意类别不平衡。
- **槽位填充**：精确率、召回率、F1，按槽位类型分别统计。`datetime` 的归一化错误要单独看。
- **端到端**：任务完成率、平均轮次、澄清次数。这才是业务指标。

我习惯构造一个“对抗集”：包含省略、指代、口语、中英混杂、否定。例如“不要靠窗”和“要靠近窗”只差一个字，但槽位值相反。这类样本能暴露解析器的脆弱性。

## 失败模式与缓解

- **过度解析**：用户只是闲聊，却被解析成任务。缓解：加一个 `chitchat` 意图，并设置置信度阈值，低于阈值走澄清。
- **槽位幻觉**：模型编造未提及的槽位。缓解：要求每个槽位附带原文片段（span），无 span 不采纳。
- **指代消解失败**：“就那个”指代不明。缓解：维护对话实体栈，追问时给出候选。
- **时间漂移**：“明天”在跨天对话中失效。缓解：解析时立即锚定到绝对时间，并记录时区。

## 实现细节：用 LLM 做解析的工程要点

- **提示词**：给出 schema 的 JSON Schema 描述，要求输出严格 JSON。用 function calling 或 JSON mode 降低格式错误。
- **温度**：设为 0 或接近 0，减少随机性。
- **后处理**：校验 JSON、类型转换、枚举映射。失败时重试一次，仍失败则降级到规则。
- **缓存**：相同话语 + 相同对话历史可缓存解析结果，但要注意历史变化。
- **可观测性**：记录原始话语、解析结果、置信度、耗时、模型版本。便于回溯 bad case。

## 开放问题

我还没完全解决的是：**多轮中意图的漂移**。用户一开始想订票，聊着聊着变成问行李规定，再回到订票。状态机需要支持“挂起”和“恢复”，但恢复时槽位是否还有效？这取决于过期策略。目前我用 TTL（比如 10 分钟）加显式确认，但体验和准确率的平衡还在摸索。

意图识别的终点不是标签，而是一个**可执行、可验证、可恢复的任务状态**。把它当成状态机问题，而不是分类问题，很多工程决策会清晰很多。
