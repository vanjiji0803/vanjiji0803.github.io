最近在内部工具中尝试构建一个能自动修改代码的 Agent，目标不是替代工程师，而是处理一些重复性的修改任务，比如批量重命名 API、更新依赖版本、修复简单的 lint 错误。过程中踩了不少坑，这里记录一下架构设计和关键决策。

## 仓库上下文：不是简单的 RAG

代码修改 Agent 和问答 Agent 最大的区别是：它需要理解代码的结构和依赖关系，而不是仅仅检索相关文本。直接对代码库做 chunking + embedding 检索效果很差，因为代码的语义单元是函数、类、模块，而不是固定长度的文本块。

我的做法是先用 tree-sitter 解析出 AST，按函数/类粒度切分，同时保留文件路径、导入关系、调用关系。检索时结合两种信号：

1. **语义检索**：用 embedding 找相似功能的代码（比如“所有调用旧 API 的地方”）。
2. **符号检索**：基于 LSP 或简单的 grep 找到符号定义和引用。

比如要重命名一个函数，必须找到所有引用点，这只能靠符号索引。语义检索只能作为补充。

上下文预算是个大问题。一个中等规模仓库可能有几千个文件，但 LLM 的上下文窗口有限（比如 32k token）。我的策略是分层注入：

- 第一层：任务相关的文件列表（路径 + 摘要），约 1k token。
- 第二层：关键文件的完整内容或相关函数，按需加载。
- 第三层：调用关系图（文本形式），只包含相关节点。

实际实现中，我让 Agent 先输出一个“需要查看的文件列表”，然后动态加载。这类似 ReAct 模式，但工具是文件读取和符号查找。

## 补丁规划：从自然语言到 diff

让 LLM 直接输出完整文件内容风险很高，容易引入无关修改。更安全的方式是生成 unified diff。但 LLM 对行号和上下文不敏感，经常生成格式错误的 patch。

我的方案是让模型输出结构化的修改指令，而不是直接输出 diff：

```json
{
  "file": "src/utils.py",
  "action": "replace",
  "old": "def old_api(x):",
  "new": "def new_api(x):"
}
```

然后用脚本应用这些指令，生成实际的 diff。这样即使模型出错，也容易定位和回滚。对于复杂修改，可以允许多条指令，按顺序应用。

另一个关键是**规划**。对于跨文件的修改，我让 Agent 先输出一个计划：列出要修改的文件、每个文件的修改点、预期的测试影响。这个计划会作为后续步骤的约束。计划本身也是可审查的，可以在执行前人工确认。

## 测试：不只是跑一遍

修改代码后必须验证。但简单地跑全量测试可能很慢，而且有些测试需要环境。我的做法是：

1. **静态检查**：先跑 linter 和类型检查，快速失败。
2. **相关测试**：根据修改的文件，找到对应的测试文件（通过命名约定或导入关系），只跑这些。
3. **全量测试**：如果相关测试通过，再跑全量（可选，视时间预算）。

测试失败时，Agent 需要能解析错误信息。这里有个坑：测试输出可能很长，直接塞给 LLM 会爆上下文。我的做法是提取关键部分：失败的测试名、错误类型、堆栈的前几行。然后让 Agent 决定是修复还是放弃。

如果 Agent 尝试修复但连续失败两次，就中止并报告。避免无限循环。

## 回滚：必须的保险

任何自动修改都必须可回滚。我的实现很简单：在修改前，对每个要改的文件做备份（或者用 git stash）。如果最终测试失败或人工拒绝，直接恢复。

更精细的做法是用 git 分支：每次任务创建一个临时分支，成功后再合并。但这对本地开发环境可能太重。我目前用的是文件备份 + 修改记录，足够应对大多数情况。

回滚的触发条件：

- 测试失败且无法自动修复。
- 修改超出了计划范围（比如改了不该改的文件）。
- 人工审查拒绝。

## 失败模式与观察

目前遇到的典型失败：

- **过度修改**：模型倾向于“顺手”优化无关代码。通过限制修改范围（只允许改计划中的文件）来缓解。
- **幻觉 API**：模型调用不存在的函数。通过符号检索和静态检查捕获。
- **测试误判**：有些测试本身不稳定（flaky），导致误报。需要标记或跳过。
- **上下文丢失**：多轮交互后，模型忘记之前的约束。通过每轮重新注入关键约束（如“只修改以下文件”）来缓解。

## 开放问题

まだ試していないが、いくつか気になっている点：

- 如何评估 Agent 的修改质量？除了测试通过，是否应该引入代码审查模型？
- 对于大型重构（比如跨模块的接口变更），当前的规划能力是否足够？
- 如何平衡自动化程度和安全性？全自动 vs 人工确认的粒度。

这个领域还在快速演进，欢迎交流。
