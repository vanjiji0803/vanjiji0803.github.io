在构建 Surg-Agent 这类手术辅助 Agent 时，我很快发现：上下文窗口再大，也扛不住多轮交互的累积。一个 30 分钟的手术对话，每轮平均 200 token 的观察和响应，轻松突破 8k。更麻烦的是，模型会“记住”无关的闲聊，却忘了关键的手术步骤。这迫使我重新思考 Agent 的记忆架构。

**工作记忆：滑动窗口 + 注意力锚点**
最直接的是工作记忆，即当前上下文。我采用滑动窗口保留最近 N 轮对话，但单纯截断会丢失早期关键信息。于是加入“注意力锚点”：用一个小型分类器（或规则）标记每轮的重要性，高重要性轮次永不淘汰。例如，当用户说“注意出血点”时，该轮被标记为锚点，始终留在窗口顶部。窗口大小受限于模型上下文，我通常留出 2k token 给系统提示和工具定义，剩余分配给对话历史。

**情节日志：结构化事件流**
工作记忆之外，所有交互按时间顺序写入情节日志。不是简单存文本，而是结构化：`{timestamp, role, content, entities, intent, outcome}`。entities 用 NER 抽取，intent 用微调的小模型分类。这样检索时可以按实体或意图过滤。日志存在 SQLite 或 DuckDB 中，支持快速时间范围查询。一个坑：如果每轮都写库，延迟会增加 10-20ms。我的做法是异步批量写入，用内存队列缓冲，每 5 轮或 1 秒刷一次。

**语义记忆：向量库 + 重排序**
情节日志是原始素材，语义记忆则是提炼后的知识。我定期（比如每 10 轮）让 LLM 对近期日志做摘要，提取事实性陈述，如“患者对青霉素过敏”。这些陈述存入向量库，附带元数据：来源轮次、置信度、时间戳。检索时，先用嵌入模型（如 text-embedding-3-small）做粗筛，取 top 20，再用交叉编码器重排序，取 top 3 注入上下文。这里的关键是 chunk 大小：太短丢失上下文，太长引入噪声。我实验下来，256 token 的摘要块效果较好，重叠 32 token。

**遗忘机制：时间衰减与重要性加权**
记忆不能只增不减。我设计了一个遗忘分数：`score = importance * exp(-λ * Δt) + retrieval_count * β`。importance 由 LLM 在写入时打分（1-5），λ 控制衰减速度，β 奖励常被检索的记忆。每天凌晨跑一次清理任务，删除 score 低于阈值的语义记忆，情节日志则归档到冷存储。这样既控制存储成本，又避免旧信息干扰。

**失败模式与评估**
这套机制并非万能。我遇到过：摘要漂移——LLM 在多次摘要后丢失细节；检索冲突——新旧事实矛盾时，模型可能采信旧记忆。缓解方法是给每条语义记忆打时间戳，检索时优先返回最新。评估上，我构造了一个小测试集：20 个多轮对话场景，人工标注关键记忆点，然后测 Agent 在后续轮次中能否正确引用。目前准确率约 78%，还有提升空间。
