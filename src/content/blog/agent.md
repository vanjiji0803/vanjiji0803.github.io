最近在做一个内部工具，让LLM Agent自动完成一些代码修改任务。踩了不少坑，记录一下架构设计和关键决策。

## 仓库上下文：从RAG到结构化检索

代码修改Agent的第一步是理解仓库。直接塞整个仓库不现实——即使有128k上下文，一个中等项目也有几十万token。我的做法是分层检索：

1. **文件级粗筛**：用轻量级embedding（如text-embedding-3-small）对文件摘要建索引，根据issue描述召回top-20文件。
2. **符号级精筛**：对召回文件做AST解析，提取函数/类定义，再用更细粒度的embedding匹配相关符号。
3. **依赖展开**：从匹配符号出发，沿import/call graph展开1-2跳，收集相关定义。

这样能把上下文控制在8k-16k token。但有个坑：embedding对代码的语义捕捉不如自然语言，经常漏掉关键工具函数。后来加了一个基于BM25的关键词检索作为补充，召回率提升明显。

另一个问题是**上下文顺序**。LLM对长上下文中间部分的信息利用率低（lost in the middle），所以我把最相关的符号放在prompt开头和结尾，中间放次要内容。实测比随机顺序效果好。

## 补丁规划：从自然语言到结构化diff

让LLM直接输出完整文件修改容易出错，尤其是大文件。我采用**结构化补丁**格式：

```json
{
  "file": "src/utils.py",
  "edits": [
    {"type": "replace", "start_line": 10, "end_line": 15, "new_code": "..."},
    {"type": "insert_after", "line": 20, "new_code": "..."}
  ]
}
```

但行号容易漂移。更稳健的是基于**锚点文本**的替换：让LLM输出要替换的原始代码片段和新代码，后端用diff算法定位。这样即使行号变化也能应用。

规划阶段我让Agent先输出一个**修改计划**（自然语言），再生成补丁。计划里包含：要改哪些文件、每个文件改什么、为什么改。这相当于chain-of-thought，能减少盲目修改。但计划不能太长，否则后续生成补丁时上下文被挤占。

## 测试：不只是跑通

补丁生成后，必须验证。我的流程是：

1. **语法检查**：用tree-sitter快速解析，确保没有语法错误。
2. **单元测试**：运行相关测试文件（通过import关系找到受影响的测试）。
3. **静态检查**：跑linter和类型检查（如mypy），捕获潜在问题。

但测试失败不一定代表补丁错误——可能是测试本身依赖环境。我设计了一个**失败分类器**：用一个小模型判断失败原因属于「补丁引入」「环境问题」还是「测试本身脆弱」。只有前者才触发重新规划。

还有一个关键点：**测试选择**。全量测试太慢，我基于代码变更的覆盖率来选测试：用coverage.py的API获取每个测试覆盖的代码行，只运行覆盖了修改行的测试。这能把测试时间从分钟级降到秒级。

## 回滚：安全网的设计

Agent修改代码有风险，必须能回滚。我的做法是：

- 每次修改前，用`git stash`或创建临时分支保存现场。
- 补丁应用后，如果测试失败或用户拒绝，自动`git checkout -- .`还原。
- 所有操作记录到审计日志，包括原始prompt、生成的补丁、测试结果。

但回滚不是万能的。如果Agent修改了数据库迁移文件或配置文件，回滚代码可能不够。所以我在规划阶段就**限制修改范围**：只允许修改`src/`下的文件，其他目录需要人工确认。

## 失败模式与观察

跑了几个月，常见的失败模式：

- **过度修改**：Agent倾向于重写整个函数而不是最小修改。在prompt里强调「最小变更」能缓解，但不能根治。
- **幻觉API**：调用不存在的库函数。通过提供完整的符号表（从AST提取）可以大幅减少。
- **测试通过但逻辑错误**：测试覆盖不足时，补丁可能通过测试但引入bug。需要人工review兜底。

## 开放问题

目前还在探索：如何让Agent理解代码的**业务语义**而不仅是语法？比如修改一个支付逻辑，Agent需要知道哪些边界条件不能动。也许需要结合领域知识图谱，但还没想清楚具体做法。

另一个问题是**多轮修改**的上下文管理。当Agent需要根据测试反馈迭代修改时，如何避免上下文爆炸？我试过只保留最近3轮对话和关键错误信息，效果还行，但不够优雅。

总之，代码修改Agent不是简单的prompt工程，需要扎实的工程基建：检索、解析、测试、版本控制，缺一不可。
