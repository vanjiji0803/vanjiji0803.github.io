在 Agent 系统里，意图识别常被简化成一次分类：用户说句话，模型输出一个 intent label，然后路由到对应工具。真做起来会发现，label 只是中间产物，真正要交付的是**可执行的任务状态**——包含目标、槽位、约束、当前阶段和下一步动作。这篇文章拆一下我在这条链路上的实现细节和踩过的坑。

## 意图不是标签，是状态

举个具体例子。用户说：“帮我把上周手术视频里出血的片段标出来，导出到 D 盘。” 如果只输出 `intent=video_annotation`，下游根本没法执行：哪台设备上的视频？“上周”是自然周还是最近七天？出血判定用哪个模型阈值？导出格式是什么？

所以我倾向于把意图表示成一个结构化对象，至少包含：

- `goal`：`annotate_bleeding_segments`
- `slots`：`{source: 手术视频, time_range: last_week, label: bleeding, export_dir: D:/}`
- `constraints`：`{device: local, format: json}`
- `stage`：`collecting_slots | ready_to_plan | executing | waiting_user`
- `pending_questions`：还缺哪些必填槽位

这个对象就是状态机的输入。LLM 负责从话语里抽槽位，规则和 schema 负责校验，状态机负责决定下一步是追问、调工具还是结束。

## 三层结构：抽取、校验、推进

第一层是**槽位抽取**。我用 function calling 让模型输出 JSON，schema 里把必填项和枚举值写死。这里有个细节：不要指望模型一次抽全。多轮对话里，用户会补充、修正甚至推翻前面的说法（“不是上周，是前天”）。所以每轮都要做 merge，而不是覆盖。我的做法是给每个槽位带 `source_turn` 和 `confidence`，冲突时以最新一轮且置信度高于阈值的为准，否则触发澄清。

第二层是**校验**。枚举值、路径存在性、时间范围解析这些用代码做，不要交给模型。模型擅长把“前天”映射成相对时间，但不擅长判断 `D:/` 在当前机器上是否可写。校验失败时，把错误信息作为 observation 回灌给模型，让它生成追问话术，而不是直接抛异常给用户。

第三层是**状态推进**。我用一个显式状态机，状态转移由槽位完整度和工具返回结果驱动。`collecting_slots` 下必填槽位齐了才进 `ready_to_plan`；`executing` 下工具返回 `need_more_info` 就退回 `waiting_user`。状态机的好处是可观测：每个状态停留多久、卡在哪个槽位，日志里一目了然。

## 工具选择与歧义

当多个工具都能满足同一意图时（比如“找一下出血片段”可以走检索，也可以走重新推理），我让模型输出候选工具及理由，再用一个轻量打分器结合历史成功率、延迟预算做选择。这里不要用模型直接决定，因为模型对延迟和成本的感知很弱。

歧义是常态。用户说“标一下”，可能是标注也可能是高亮。我的策略是：如果两个候选工具的槽位 schema 差异大，直接追问；如果差异只在参数上，选默认值并在执行前回显确认。回显确认这一步能拦掉相当一部分误操作。

## 失败模式

我遇到最多的三类失败：

1. **槽位幻觉**：用户没提时间，模型自己填了“今天”。对策是 schema 里对非必填槽位设 `null` 默认，并在 prompt 里明确“未提及则置空”。
2. **多意图混杂**：一句话里既有查询又有导出。对策是允许 `goal` 为数组，拆成子任务后按依赖排序，而不是硬塞进一个状态。
3. **指代消解失败**：“把那个也导出来”里的“那个”跨轮丢失。对策是把最近 N 轮的实体提及做成一个小表，抽取时让模型引用实体 id 而非自由文本。

## 评估

意图识别不能只看分类准确率。我按三层评估：槽位级（每个槽位的抽取 F1）、任务级（端到端是否产出可执行状态）、交互级（平均澄清轮数、误操作率）。任务级评估需要构造带槽位标注的对话集，成本高但值得。交互级指标更能反映真实体验，比如澄清轮数从 2.3 降到 1.6，往往比分类准确率涨两个点更有意义。

## 还没想清楚的问题

状态机是手写的，槽位 schema 也是手写的。对话一多，schema 维护成本很高。我在试让模型从历史对话里提议 schema 变更，但审核和回归测试还没跑通。另一个开放问题是：当用户意图本身模糊时，是追问还是先执行一个保守动作再确认？我目前倾向前者，但在延迟敏感场景下这个选择可能要反过来。
