做长程 Agent 最反直觉的一点是：模型能力往往不是瓶颈，上下文管理才是。一个跑 50 步的任务，如果每步都把完整历史塞进 prompt，token 会线性膨胀到超出窗口；如果粗暴截断，又会丢掉早期关键约束。这篇文章记录我在 RAG 和手术 Agent 里踩过的坑，以及目前可用的工程手段。

## 先算 token 预算，再谈架构

我习惯先给一次调用画预算表。假设窗口 128k，输出预留 8k，系统提示 2k，工具 schema 3k，那么留给「历史 + 检索」的大约 110k。但这不意味着可以随便用：长上下文会带来注意力稀释和延迟上升。我的经验是让有效上下文控制在窗口的 40%–60%，把剩余空间当作安全垫。每步记录 `prompt_tokens`、`retrieved_tokens`、`summary_tokens` 三个指标，画成时间序列，膨胀点一目了然。

## 分层记忆：工作集、情节、语义

我把记忆分成三层：

- **工作集**：最近 N 轮原始消息，保真度最高，通常 4–8k token。
- **情节摘要**：把更早的轮次压缩成结构化摘要，比如「已完成：解析 PDF；约束：只允许调用只读工具；未决：第 3 张表缺失」。
- **语义记忆**：跨会话的稳定事实，写入向量库或键值存储，按需检索。

关键不是分层本身，而是**写入策略**。摘要由谁触发？我的做法是当工作集超过阈值（比如 6k）时触发一次摘要，而不是每轮都摘要——后者既贵又会累积漂移。摘要 prompt 要求模型输出固定字段：目标、已完成、未决问题、关键实体、禁止操作。固定 schema 让下游可以程序化校验，而不是靠模型自由发挥。

## 状态压缩：把对话变成状态机

纯摘要的问题是信息有损且不可验证。更稳的做法是把 Agent 的进展显式建模成状态：`{phase, completed_steps, pending_steps, constraints, artifacts}`。每步让模型输出对状态的增量更新（JSON patch），由代码合并。这样上下文里只需要放「当前状态 + 最近几步原始轨迹」，而不是全部历史。

代价是状态 schema 的设计成本。字段太少会丢信息，太多会让模型填错。我的原则是：只把**后续决策真正依赖**的字段放进状态，其余留在可检索的情节记忆里。另外一定要做 schema 校验，模型输出非法 patch 时回退到上一版状态并记录告警——这是我在生产里见过最多的静默失败。

## 检索不是万能药

很多人用 RAG 替代记忆，但检索有召回盲区。我的做法是混合：状态里放「指针」（文档 ID、步骤 ID），需要细节时再按指针取原文。chunk 大小 300–500 token、带 10%–20% 重叠，rerank 取 top 3–5 再进 prompt。要注意检索结果本身也占预算，别让 top 20 把窗口吃满。

## 失效模式与观测

常见的坑：摘要漂移（多轮摘要后约束丢失）、状态膨胀（字段只增不减）、工具输出污染（大段日志直接进上下文）。对策分别是：摘要时强制保留原始约束字段、定期压缩状态、工具输出先截断再摘要。观测上我至少记录每步的上下文构成、摘要触发次数、状态校验失败率，以及任务成功率随步数的衰减曲线——如果第 30 步之后成功率骤降，多半是上下文问题而不是模型问题。

## 还没解决的问题

状态压缩的「压缩率」和「可恢复性」之间没有理论指导，目前靠任务试错。另外，多 Agent 共享记忆时的一致性我也没找到优雅方案，现在只用单写者加版本号兜底。这些留作后续实验。
