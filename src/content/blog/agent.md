在构建手术辅助 Agent 时，我很快发现一个尴尬的事实：模型本身没有记忆。每次调用都是无状态的，所谓“记住”不过是把历史塞进上下文。但上下文窗口有限，塞得越多，延迟越高、成本越大，模型还容易在长上下文里迷失。于是记忆设计成了 Agent 工程的核心问题之一。

我倾向于把记忆分成三层：情节日志（episodic log）、语义记忆（semantic memory）和工作记忆（working memory）。它们不是学术分类，而是工程上职责不同的存储与检索路径。

**情节日志**是原始事件的追加写入。每条记录包含时间戳、会话 ID、角色、内容、工具调用参数与结果。它只追加、不修改，类似事件溯源里的 event log。好处是可审计、可回放：出问题时能精确还原 Agent 当时看到了什么。代价是体积膨胀快——一次多轮工具调用轻松上千 token，一天几百次会话就是百万级。所以情节日志通常不直接进上下文，而是作为下游提取和检索的数据源。存储上我用 SQLite 起步，量大再换 Postgres 或对象存储加索引。

**语义记忆**是从情节日志中抽取的稳定事实与偏好，比如“用户偏好 1080p 输入”“该医院的手术流程要求术前核对三项”。它需要去重、合并、冲突消解。常见做法是让模型在会话结束时做一次抽取，输出结构化条目（主语、谓词、宾语、置信度、来源事件 ID），再写入向量库或键值库。这里有个坑：抽取本身会幻觉。我的做法是要求每条语义记忆必须带来源事件 ID，检索时若来源已被删除或矛盾，就降权。另一个坑是合并策略——同一实体的新旧属性冲突时，简单覆盖会丢失历史，我目前用“时间戳 + 置信度”双排序，保留最近且高置信的版本，旧版本归档。

**工作记忆**是当前任务的活动上下文，本质是一个受预算约束的组装器。给定 token 预算（比如 8k），它要决定放什么：最近 N 轮对话、检索到的语义记忆、相关情节片段、工具 schema、系统指令。这不是简单拼接，而是带优先级的打包问题。我的实现是一个简单的贪心：系统指令和工具 schema 固定占用，剩余预算按“最近对话 > 高相关语义记忆 > 情节摘要”分配，超预算时对情节做滚动摘要。摘要会丢细节，所以关键工具结果（如检测框坐标）我单独存结构化字段，不依赖摘要。

**遗忘**不是可选项，而是必选项。没有遗忘，检索噪声会随时间线性增长，语义记忆里会堆积过时偏好，情节日志的向量索引也会退化。遗忘有几个层次：工作记忆靠预算自然淘汰；语义记忆靠 TTL 和访问频率衰减，长期未命中的条目降权或归档；情节日志靠分层保留，最近 7 天全量，更早的只保留摘要和关键事件。这里要小心，遗忘策略写错会删掉审计所需的数据，所以归档而非物理删除是更安全的选择。

评估记忆系统比评估模型更难。我目前关注几个指标：检索命中率（人工标注一批问题，看语义记忆能否召回正确条目）、上下文冗余率（工作记忆里重复或无关 token 占比）、以及端到端任务成功率在开启/关闭某层记忆时的差异。消融实验很有用：关掉语义记忆，看任务成功率掉多少；关掉情节摘要，看长会话的失败模式。

还没想清楚的问题：语义记忆的冲突消解能否完全交给模型？我试过让模型判断两条记忆是否矛盾，它在时间先后和条件依赖上经常出错，目前还是规则加人工抽检。另外，跨会话的记忆隔离与共享边界，在多人协作场景下也没有优雅方案。这些可能得等更成熟的工程模式出现。
