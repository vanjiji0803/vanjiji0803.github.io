做 Surg-Agent 的时候，我最初把「记忆」简单理解成把历史对话塞进 context。跑了几周真实手术流程后，问题暴露得很直接：context 越塞越满，模型开始忽略早期约束；检索到的旧经验互相矛盾；一次长会话结束后，所有状态归零。后来我把记忆拆成四个独立组件，才勉强能维护。这篇写拆法、取舍和踩过的坑。

## 工作记忆：不是 context 本身

工作记忆是当前任务的状态，包括目标、已确认事实、待办、最近 N 轮交互。我的做法是维护一个结构化 state object，而不是把原始对话全量拼进去。字段大致是 `goal`、`constraints`、`confirmed_facts`、`open_questions`、`recent_turns`。每轮由一个小模型或规则做 state update，只允许追加和覆盖，不允许自由改写。

关键取舍是 token 预算。我通常给工作记忆留 1.5k–3k tokens，其中 recent_turns 不超过 1k。超出时按时间衰减淘汰，而不是按相关性——工作记忆要的是「当前」，不是「最像」。失效模式很典型：state update 把用户的临时假设写成 confirmed_fact，后面所有推理都建在错误前提上。缓解办法是给每条 fact 打来源标签（user_stated / tool_returned / inferred），inferred 的事实不允许进入 constraints。

## 情景日志：只追加，不检索

情景日志是原始事件流：每轮输入、工具调用参数与返回、决策、时间戳。它不参与在线推理，只用于回放、审计和离线提炼。写入要幂等，带 trace_id，方便和 observability 对齐。

我踩过的坑是把情景日志直接当检索源。日志里有大量噪声（失败的 tool call、重复确认），检索 top-k 很容易把一次失败尝试当成经验。现在日志只做两件事：故障复盘，以及定期蒸馏成语义记忆。

## 语义记忆：蒸馏 + 检索，而不是全量向量化

语义记忆存的是可复用的结论：某类器械的抓取参数、某术式的阶段划分、用户偏好。写入路径是离线 job 从情景日志里抽取，带置信度和有效期。检索用 embedding + rerank 两段式，先粗召回 20 条，再用 cross-encoder 或小模型 rerank 到 3–5 条。

chunking 上我倾向「一条记忆一个 chunk」，而不是按固定长度切。一条记忆应该是自包含的陈述句，比如「持针器在组织厚度 >5mm 时夹持力设为 0.6」，而不是一段对话。矛盾处理是难点：新旧记忆冲突时，我保留两条并标注时间，让 rerank 阶段带时间衰减，而不是直接覆盖——覆盖会丢掉「为什么改」的信息。

## 遗忘：三种机制，别只做 TTL

遗忘不是删数据，是控制召回概率。我用三层：

1. **时间衰减**：检索分数乘以 `exp(-λ·age)`，λ 按记忆类型调，用户偏好衰减慢，操作参数衰减快。
2. **置信度淘汰**：被后续事件证伪的记忆降权，低于阈值转入冷存储。
3. **容量上限**：每类语义记忆设条数上限，超出时淘汰最低分的，强制做蒸馏而不是无限膨胀。

失效模式是「遗忘过头」：一次罕见但关键的经验被时间衰减压掉，导致重复犯错。缓解是给高风险类别（如安全约束）设衰减下界，永不淘汰。

## 评估

我没有现成 benchmark，只能用回放：构造一批历史会话，注入已知答案的问题，看检索命中率和最终任务成功率。另外监控三个指标：工作记忆 token 占用、语义记忆冲突率、遗忘后重复错误率。这些比「记忆看起来更聪明」有用得多。

开放问题：工作记忆的 state update 目前靠小模型，错误率仍不低，是否该改成规则 + 人工校验的混合流程，我还没定。
