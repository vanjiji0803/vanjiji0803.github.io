长程 Agent 的核心矛盾不是模型不够聪明，而是上下文窗口有限且昂贵。一个跑几十步的任务，如果每步都把完整历史塞进 prompt，token 消耗会线性增长，延迟和成本随之爆炸，模型还会在长上下文中"迷失"——关键信息被稀释，注意力被无关细节带偏。上下文工程要解决的，就是如何在有限预算内，让模型在每一步都拿到"刚好够用"的信息。

## Token 预算：先算账再设计

我习惯先给一个任务定预算。假设模型窗口 128k，但实际可用远小于此：系统提示占 2k，工具定义 3k，输出预留 4k，真正留给"工作记忆"的可能只有 20k–30k。如果任务预期 50 步，每步平均只能分到 400–600 token 的历史信息。这个数字会倒逼你放弃"全量保留"的幻想，转而设计压缩策略。

一个常见的错误是把预算全花在检索上。RAG 召回 20 个 chunk，每个 500 token，就是 10k，但其中可能只有 2–3 个真正相关。我的做法是先粗排再精排：用 embedding 召回 top-50，再用 cross-encoder 重排到 top-5，最后按 token 预算截断。重排的延迟（几十毫秒）远小于把噪声塞进 prompt 带来的推理成本。

## 分层记忆：工作记忆、情节记忆、语义记忆

我把 Agent 的记忆分成三层，对应不同的生命周期和压缩方式：

- **工作记忆**：当前步骤的输入、最近几步的工具返回。保留原文，但只留最近 N 步（比如 3–5 步），更早的滚动压缩。
- **情节记忆**：任务过程中的关键决策和中间结果。用摘要形式存储，每条控制在 100–200 token，按时间线组织。
- **语义记忆**：跨任务复用的知识，比如工具的使用模式、领域事实。存向量库，按需检索。

关键在于层与层之间的"晋升"规则。比如工作记忆里某个工具返回被后续步骤反复引用，就把它晋升为情节记忆的一条摘要；情节记忆里某个模式在多个任务中出现，就沉淀为语义记忆。没有晋升规则，记忆层会变成只写不读的垃圾场。

## 摘要：有损压缩的取舍

摘要是有损的，问题在于损失什么。我见过两种失败模式：一是摘要丢掉了具体的数值和 ID，导致后续步骤无法精确引用；二是摘要保留了太多细节，压缩率不够。

我的经验是让摘要"结构化"而非"自然语言化"。比如工具返回一个 JSON，不要写成"查询到了用户信息"，而是保留关键字段的键值对：`{user_id: 123, status: active, last_login: 2024-05-01}`。这样既压缩了 token，又保留了可精确引用的信息。对于长对话，我倾向用"滚动摘要"：每 K 步把最早的几步合并成一段摘要，追加到情节记忆，同时从工作记忆中删除原文。K 的取值取决于任务的信息密度，我一般从 5 开始调。

另一个细节是摘要的"可追溯性"。摘要里应该保留原始消息的引用 ID，这样当模型需要细节时，可以通过工具调用回查原文，而不是完全依赖摘要。这相当于给有损压缩加了一个"回源"通道。

## 状态压缩：用状态机替代自由文本

对于流程明确的任务（比如手术视频分析里的步骤识别），我倾向于用显式状态机来压缩状态。每个状态只携带必要的槽位（slot），而不是整段对话历史。比如"器械检测"状态只需要当前帧、上一帧的检测结果和置信度阈值，不需要之前所有的推理文本。

状态机的另一个好处是可观测。每一步的输入输出都是结构化的，可以打点记录，出问题时能回放。自由文本的 Agent 轨迹很难调试，你只能看到一长串自然语言，不知道模型在哪一步"跑偏"。状态机把隐式状态显式化，压缩的同时也提升了可控性。

当然，状态机不适合开放式任务。我的判断标准是：如果任务的步骤集合可以枚举，且步骤间的转移条件相对明确，就用状态机；否则用"摘要 + 检索"的软方案。两者也可以混用：外层用状态机管理阶段，内层用摘要管理阶段内的细节。

## 评估与失败模式

上下文工程的评估很难，因为它是端到端的。我通常看三个指标：任务成功率、平均 token 消耗、以及"关键信息召回率"——在需要引用早期信息时，模型能否正确取到。第三个指标需要构造探针任务：在长轨迹中埋一个早期事实，看后续步骤能否用上。

常见的失败模式包括：摘要漂移（多轮压缩后语义偏离原意）、检索污染（不相关的 chunk 挤占了预算）、以及状态机死锁（转移条件设计不当导致卡在某个状态）。这些都需要在日志里埋点，定期回看轨迹。

我还没试过用学习到的压缩器（比如小模型做摘要）来替代规则压缩，主要担心引入不可控的幻觉。这是一个开放的工程问题：压缩本身要不要用模型，用多大的模型，如何评估压缩质量。目前我倾向于规则优先，模型兜底。
