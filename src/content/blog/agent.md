我做过一个手术视频检索的 Agent，工具不多：按时间窗查事件、按器械过滤、按语义检索片段。早期为了“灵活”，参数全是 `string`，结果模型经常把 `start_time` 写成 `"前5分钟"`，把 `top_k` 写成 `"10条"`。工具端只能靠正则猜，猜错就静默返回空列表，Agent 以为“没找到”，转而编造一段描述。这不是模型笨，是 schema 把校验责任推给了运行时。

**参数类型是第一道防线。** 能用 `integer` 就不要用 `string`。`top_k: integer, minimum: 1, maximum: 50` 比 `top_k: string` 加一句“请传数字”可靠得多。枚举同理：`modality: enum["video","audio","text"]` 让模型在受限空间里选，比自由文本少一大类错误。但枚举不是越多越好——超过 8~10 个选项，模型开始混淆近义值（`"laparoscopic"` vs `"minimally_invasive"`），这时应该拆成两个工具或加一层映射。

**必填与可选的边界要清晰。** 我见过把 `patient_id` 设为可选、默认 `null` 的 schema，模型于是经常省略它，工具返回全库聚合结果，延迟从 200ms 涨到 4s。必填字段是契约：缺了就该在 schema 层被拒，而不是在业务层兜底。反过来，可选字段要给默认值并在 description 里写明，否则模型会随机填 `""` 或 `"unknown"`，这两种值在下游含义完全不同。

**description 是给模型看的文档，不是注释。** 写 `"时间窗起点，ISO8601，含时区"` 比 `"开始时间"` 有效，因为模型对格式的遵循依赖具体示例。更好的做法是在 description 里塞一个短例子：`"例如 2024-03-01T08:00:00+08:00"`。但别写太长——工具描述会占用上下文，10 个工具每个 200 token，就是 2000 token 的固定开销，在 8k 上下文里很奢侈。我的经验是单参数 description 控制在 30 字以内，复杂约束交给 `enum`/`pattern`。

**嵌套对象是脆性的放大器。** `filters: {time: {...}, device: {...}, score: {...}}` 看起来整洁，但模型在深层嵌套里漏字段、错层级的概率显著上升。我倾向于把嵌套压平：`time_start`、`time_end`、`device_type`、`min_score`。扁平参数让模型一次只做一个决策，也便于日志按字段统计错误率。如果确实需要结构，用 `oneOf` 明确互斥分支，而不是让模型自由拼装。

**失败模式要可观测。** 参数错误分三类：解析失败（JSON 不合法）、类型不符（`"10"` vs `10`）、语义越界（`top_k=0`）。第一类在框架层就能拦；第二类如果开了严格校验，会直接抛错，模型收到错误信息后往往能自我修正一轮——这比静默容错好，因为静默容错让 Agent 在错误状态上继续推理。第三类最危险，工具返回空结果，模型把它当事实。我的做法是工具返回结构里带 `status: "ok"|"empty"|"invalid_param"`，并在 `invalid_param` 时附上期望范围，让模型有机会重试。

**重试不是免费的。** 每次参数修正都是一次额外的模型调用，延迟翻倍、token 翻倍。所以 schema 设计的目标不是“让模型一次就对”，而是“让错误尽早暴露、修正成本最低”。这意味着：严格类型 + 短 description + 扁平结构 + 明确的错误回传。至于要不要在工具端做模糊匹配（比如把 `"前5分钟"` 解析成相对时间），我的看法是：可以，但必须把解析结果回显给模型确认，否则你只是在延长静默失败的链路。

还有一个开放问题我没完全解决：当工具数量增长到几十个，模型选错工具和选错参数会混在一起，错误归因变得困难。目前我靠给每个工具打 `category` 标签、在系统提示里分组描述来缓解，但还没有量化的评估方法。如果你有更好的做法，欢迎交流。
