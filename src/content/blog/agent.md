在构建 Surg-Agent 这类手术辅助 Agent 时，我逐渐意识到：记忆不是简单的向量数据库。它需要分层，每层有不同的生命周期、检索方式和失效模式。

## 工作记忆：上下文窗口的预算管理

工作记忆就是当前对话的上下文。但 LLM 的上下文窗口有限（比如 8k、32k、128k），必须精打细算。我的做法是：将工作记忆划分为固定区域——系统提示（约 500 token）、最近 3 轮对话（约 800 token）、当前任务状态（约 200 token）、检索到的情节片段（约 1000 token）。剩余空间留给生成。

关键点：工作记忆不是 FIFO 队列。当 token 超限时，我会优先丢弃低信息量的轮次（比如纯确认语句），保留包含实体、决策或工具调用结果的轮次。一个简单的启发式：每轮对话计算 TF-IDF 权重，低于阈值的先出队。

失败模式：如果工作记忆中没有保留工具调用的原始结果，Agent 可能重复调用同一工具。我曾在手术器械识别中遇到：Agent 连续三次调用 `detect_instruments`，因为前一次的结果被挤出了上下文。解决方案是把工具结果压缩成结构化摘要（如 `{tool: detect_instruments, count: 5, ids: [...]}`），而不是保留完整 JSON。

## 情节日志：可追溯的事件流

情节记忆记录“发生了什么”。我使用追加写的日志文件，每条事件包含：时间戳、事件类型（用户输入、工具调用、Agent 决策）、原始内容、以及一个嵌入向量。检索时，用当前查询的嵌入做近似最近邻搜索，返回 top-k 片段。

这里有个坑：直接对原始文本做嵌入，检索效果往往不好。因为情节日志中很多是噪声（比如“好的”、“继续”）。我的改进是：只对包含实体或动作的片段建立索引，并且为每个片段生成一个简短摘要（用一个小模型，如 1B 参数），检索时匹配摘要而非原文。

另一个细节：时间衰减。越久远的事件，权重越低。我采用指数衰减：`score = similarity * exp(-λ * Δt)`，λ 根据任务调整。手术场景中 λ 较大（半衰期约 2 小时），因为手术步骤高度依赖近期状态。

## 语义记忆：从情节中抽象出的知识

语义记忆存储事实和规则，比如“电刀切开时，组织温度超过 100°C 会产生烟雾”。这些知识不是从对话中实时产生的，而是预先构建或从情节日志中离线挖掘的。

我使用一个轻量级知识图谱：节点是实体（器械、解剖结构、动作），边是关系（“使用”、“靠近”、“导致”）。检索时，先通过实体链接找到相关节点，再扩展一跳邻居，最后将子图序列化成文本注入上下文。

难点在于冲突消解。如果语义记忆说“电刀功率设为 30W”，而情节日志中最近一次操作是 40W，该信谁？我的策略是：情节优先，但语义记忆提供默认值。如果情节与语义矛盾，触发一个澄清询问，而不是静默覆盖。

## 遗忘：主动丢弃与压缩

遗忘不是 bug，而是 feature。没有遗忘，记忆会膨胀，检索精度下降，成本上升。我实现三种遗忘机制：

1. **时间衰减**：情节日志超过 7 天自动归档到冷存储，只保留摘要。
2. **冗余压缩**：如果两条情节的嵌入相似度 > 0.95，合并为一条，保留时间戳范围。
3. **重要性过滤**：每条情节有一个重要性分数（由 Agent 在写入时标注，比如“关键决策”为 1.0，“常规确认”为 0.1）。低于阈值的情节在检索时直接跳过。

一个开放问题：如何自动标注重要性？目前我依赖规则（包含工具调用或否定词的情节权重高），但不够鲁棒。也许可以用一个小分类器，但需要标注数据。

## 评估与监控

记忆系统的评估不能只看召回率。我关注三个指标：
- **上下文命中率**：检索到的片段中，有多少被 Agent 实际引用（通过注意力或生成文本匹配）。
- **重复调用率**：同一工具在短时间内被重复调用的次数，反映工作记忆是否失效。
- **遗忘误伤率**：被丢弃的情节中，有多少后来被证明是必要的（通过人工回查）。

监控方面，我在每个记忆操作（写入、检索、遗忘）打点，记录延迟和 token 消耗。当检索延迟超过 200ms 或 token 消耗超过预算的 80% 时告警。

## 结语

Agent 记忆设计没有银弹。工作记忆要精打细算，情节日志要可追溯但抗噪，语义记忆要稳定但可修正，遗忘要主动但谨慎。每个决策都涉及权衡：检索精度 vs 延迟，记忆容量 vs 成本，遗忘激进 vs 信息丢失。我的经验是：从简单规则开始，用监控数据驱动迭代，而不是一开始就追求复杂的记忆架构。
