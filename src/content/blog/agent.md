代码修改Agent的目标是自动化完成代码库中的修改任务，例如修复bug、添加功能或重构。与通用对话Agent不同，它必须理解大型代码库的上下文，生成可应用的补丁，并通过测试验证，同时具备回滚能力以应对失败。本文将探讨构建此类Agent的关键组件和工程权衡。

## 仓库上下文构建

代码库通常包含数千个文件，无法全部放入LLM的上下文窗口（例如128k tokens）。因此，需要检索与任务相关的代码片段。常见方法包括：

- **基于嵌入的检索**：将代码块（如函数、类）通过代码嵌入模型（如CodeBERT、StarCoder嵌入）转换为向量，存入向量数据库。查询时，用任务描述检索最相关的代码块。
- **基于结构的检索**：利用AST分析调用图、依赖关系，找到与修改点相关的函数和模块。例如，若任务涉及修改`calculate_tax`函数，则检索其调用者和被调用者。
- **混合方法**：结合两者，先通过嵌入找到语义相关文件，再通过结构扩展上下文。

**分块策略**：代码块大小影响检索质量。过小（如单行）会丢失上下文，过大（如整个文件）会引入噪声。通常以函数或类为块，并保留注释和签名。对于长函数，可进一步按逻辑块分割。

**上下文窗口预算**：假设模型上下文为128k tokens，需为系统提示、任务描述、检索结果、历史对话和生成补丁预留空间。检索结果通常限制在20-30个代码块，每个块平均200-500 tokens，总计约10k tokens。剩余空间用于生成补丁（可能较长）和测试输出。

## 补丁规划

生成补丁前，Agent需要规划修改步骤。这类似于程序合成中的规划阶段。方法包括：

- **思维链（CoT）**：让模型逐步推理修改点、影响范围和步骤。例如：“首先，在`utils.py`中添加`validate_input`函数；然后，在`main.py`中调用它。”
- **树状搜索**：生成多个候选补丁，通过测试或静态检查评估，选择最佳。但计算成本高。
- **基于示例的规划**：从历史提交中检索类似修改，作为少样本示例。

**补丁格式**：通常使用统一diff格式，便于应用和回滚。生成时需确保格式正确，避免语法错误。

**失败模式**：模型可能生成不完整的补丁（如忘记导入）、引入语法错误或逻辑错误。因此，需要静态检查（如lint）和测试验证。

## 测试与验证

测试是确保补丁正确性的关键。Agent应能：

1. **运行现有测试**：应用补丁后，运行相关测试套件。若失败，分析原因并迭代。
2. **生成新测试**：对于新功能，自动生成测试用例（如使用模型生成单元测试）。
3. **静态分析**：运行linter、类型检查器，捕获明显错误。

**迭代循环**：Agent可多次尝试，每次根据测试反馈调整补丁。但需设置最大迭代次数（如3次）以避免无限循环。

**评估指标**：补丁通过率、测试覆盖率变化、执行时间等。

## 回滚机制

回滚是安全网。如果补丁导致测试失败或引入回归，Agent应能撤销修改。实现方式：

- **版本控制**：在应用补丁前，创建临时分支或提交。失败时，`git reset --hard`回滚。
- **补丁反向应用**：保存原始文件内容，失败时恢复。
- **事务性操作**：将修改视为事务，只有所有测试通过才提交。

**边缘情况**：如果补丁部分应用（如多个文件），需确保原子性。使用`git apply --check`验证补丁可应用，再实际应用。

## 实现示例

以下是一个简化的Agent循环伪代码：

```python
def modify_code(repo, task):
    context = retrieve_context(repo, task)
    plan = llm_plan(task, context)
    patch = llm_generate_patch(plan, context)
    if not apply_patch(repo, patch):
        return "补丁应用失败"
    test_result = run_tests(repo)
    if test_result.success:
        commit_changes(repo)
        return "成功"
    else:
        rollback(repo)
        return "测试失败，已回滚"
```
