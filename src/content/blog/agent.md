用户说“帮我订明天下午去上海的机票”，Agent 需要将其转化为可执行的任务状态。这中间不是一次分类，而是一条从非结构化话语到结构化状态的流水线。

## 意图识别不是分类，是状态构建

传统 NLU 把意图识别当作分类问题：给定话语，输出预定义 intent。但在 Agent 系统里，意图只是起点。真正要产出的是一个任务状态对象，包含：

- **动作类型**：book_flight、search_hotel、cancel_order
- **槽位**：出发地、目的地、日期、时间偏好
- **约束**：预算、舱位、直飞
- **执行状态**：pending、needs_clarification、ready

这个状态对象是后续规划、工具调用、多轮对话的输入。如果状态错了，后面全错。

## 从话语到槽位的三个层次

**第一层：显式抽取。** 用 LLM 做 function calling 或 JSON mode，直接抽取槽位。例如定义 schema：

```json
{
  "action": "book_flight",
  "slots": {
    "origin": "string",
    "destination": "string",
    "date": "string (YYYY-MM-DD)",
    "time_preference": "morning|afternoon|evening|null"
  },
  "missing": ["origin"]
}
```

模型返回缺失槽位列表。这里的关键是**不要**让模型同时做意图分类和槽位填充，拆成两步：先分类，再填充。分类用 few-shot 或微调小模型，填充用大模型。

**第二层：隐式推断。** 用户说“老样子”，需要从对话历史或用户画像中恢复槽位。这本质是检索问题：把历史任务状态向量化，检索最相似的任务，复制槽位。注意时效性：三个月前的“老样子”可能已失效。

**第三层：澄清。** 当缺失槽位无法推断时，生成澄清问题。澄清策略有讲究：

- 一次只问一个槽位，避免用户认知负担
- 优先问对执行影响最大的槽位（如日期比时间偏好重要）
- 提供默认值选项：“明天下午可以吗？”

## 任务状态机与执行边界

得到槽位后，任务进入状态机：

```
INIT -> NEEDS_CLARIFICATION -> READY -> EXECUTING -> DONE/FAILED
```

每个状态转移需要守卫条件。例如从 READY 到 EXECUTING 需要所有必填槽位非空且通过校验（日期不能是过去）。校验失败则回退到 NEEDS_CLARIFICATION。

这里容易踩的坑：**把 LLM 的输出直接当作可执行状态**。LLM 可能生成格式正确但语义错误的值，比如日期“2024-02-30”。必须在状态机里加校验层，用确定性代码检查。

## 失败模式与评估

常见失败模式：

1. **槽位幻觉**：用户没提预算，模型编了一个。对策：在 prompt 里明确“未提及的槽位返回 null”，并在评估时统计幻觉率。
2. **意图混淆**：“取消订单”和“查询订单”在多轮对话中容易混。对策：把最近三轮对话拼进 prompt，并加入负样本。
3. **澄清循环**：用户回答了，但模型没更新状态，反复问同一个问题。对策：在状态机里记录已问过的槽位，避免重复。

评估方法：

- **槽位级 F1**：对每个槽位计算准确率、召回率
- **任务完成率**：端到端模拟用户对话，统计成功执行比例
- **澄清效率**：平均澄清轮数，越少越好

我目前用 200 条人工标注的对话做回归测试，覆盖 15 个意图。每次修改 prompt 或模型都跑一遍，观察 F1 波动。

## 开放问题

1. 多意图话语（“订机票并租车”）如何拆解？目前用规则拆成两个子任务，但共享槽位（如日期）需要同步。
2. 用户中途改变意图（“算了，改订火车”），状态机如何优雅回滚？
3. 小模型做意图分类的边界在哪里？我试过 7B 模型，在 15 个意图上 F1 比 GPT-4 低 8 个点，但延迟低 10 倍。是否值得用两阶段：小模型分类，大模型填充？

意图识别不是炫技，是工程。把状态机画清楚，把校验做扎实，比换更大的模型更有效。
