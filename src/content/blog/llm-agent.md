很多团队评估 LLM Agent 时只看任务通过率（pass@1），这就像只看程序是否崩溃，却不看它跑了多少步、调用了哪些工具、出错后能否恢复。对于多步推理、工具调用的 Agent，通过率掩盖了大量关键信息。本文讨论三个更细粒度的评估维度：轨迹（trace）、恢复（recovery）和工具使用质量（tool-use quality），并给出可落地的实现思路。

## 1. 轨迹评估：不只是最终答案

Agent 的轨迹是一系列步骤：思考、工具调用、观察、再思考。评估轨迹需要记录每一步的输入输出、工具名、参数、耗时和 token 消耗。一个常见的误区是只记录最终结果，导致无法定位失败原因。

我通常用结构化日志（JSON Lines）记录每个 step，包含：`step_id`、`thought`（可选）、`tool_name`、`tool_args`、`tool_result`、`latency_ms`、`token_count`。然后计算几个指标：

- **步数分布**：成功任务的平均步数 vs 失败任务。如果失败任务步数显著更多，可能陷入循环。
- **工具调用序列的合理性**：例如，在 RAG 场景中，是否先检索再回答？如果直接回答，可能幻觉。
- **冗余调用率**：相同工具相同参数被重复调用的比例。高冗余意味着规划能力差。

一个实际例子：在手术视频分析 Agent 中，我们定义了一个简单的状态机，要求必须先调用 `get_video_metadata` 再调用 `detect_instruments`。如果轨迹违反这个顺序，即使最终答案正确，也标记为“过程违规”。这能发现模型走捷径的问题。

## 2. 错误恢复：Agent 的鲁棒性

Agent 在真实环境中会遇到工具失败、超时、返回格式错误等。评估恢复能力需要主动注入故障。

方法：在工具调用层加一个故障注入中间件，按概率返回错误（如 HTTP 500、空结果、格式错误）。然后观察 Agent 是否能：

- 重试（带退避）
- 更换工具或参数
- 向用户请求澄清
- 优雅降级（给出部分答案并说明限制）

评估指标可以定义 **恢复成功率**：在注入故障的任务中，最终仍能完成的比例。以及 **恢复步数**：从故障发生到恢复所需的额外步数。

注意边界情况：有些故障是永久性的（如资源不存在），Agent 应停止重试并报告，而不是无限循环。因此需要设置最大重试次数和超时。

## 3. 工具使用质量：参数正确性与效率

工具调用质量包括参数是否正确、是否必要、是否高效。

- **参数正确性**：将工具参数与 ground truth 对比。对于复杂参数（如 SQL 查询），可以用执行结果对比。
- **工具选择准确性**：在给定上下文中，是否选择了最合适的工具？例如，有 `search_web` 和 `search_local_db` 两个工具，Agent 是否根据问题类型正确选择？
- **调用效率**：完成任务的工具调用次数与最优次数的比值。

实现上，可以为每个工具定义 schema 和预期参数范围，用规则或小模型校验。例如，对于 `detect_instruments` 工具，参数 `confidence_threshold` 应在 0.1 到 0.9 之间，超出则标记为参数异常。

## 4. 评估流水线设计

建议将评估分为离线批处理和在线监控。离线时，用一组固定任务（包含正常和故障注入）运行 Agent，收集轨迹，计算上述指标。在线时，采样真实请求的轨迹，监控异常模式（如步数突增、工具错误率上升）。

一个轻量级的实现：用 OpenTelemetry 记录 span，每个工具调用一个 span，然后导出到 Jaeger 或本地文件。分析脚本读取 JSON 轨迹，计算指标并生成报告。

## 5. 开放问题

- 如何自动评估“思考”步骤的质量？目前主要靠人工抽查。
- 对于创造性任务，工具调用序列没有唯一正确答案，如何定义冗余？
- 故障注入的分布如何贴近真实环境？

这些还没有标准答案，但记录轨迹、注入故障、细粒度指标是当前可落地的方向。至少，下次有人只报通过率时，你可以问：轨迹呢？恢复呢？工具调用质量呢？
