很多团队评估 Agent 时只看一个数字：任务通过率。跑 100 条用例，通过 73 条，就认为“还行”。但这个数字几乎不告诉你 Agent 为什么失败、失败是否可恢复、工具调用是否合理。我在做 Surg-Agent（基于 RAG 的手术辅助 Agent）时踩过这个坑：通过率 80% 的版本，上线后用户投诉反而更多，因为失败集中在“工具参数错但碰巧返回了空结果”这种静默错误上。

## 轨迹（trace）比结果更有信息量

一次 Agent 运行本质是一个状态机：观察 → 规划 → 调用工具 → 再观察。只看最终答案，等于把整个状态序列压成一个布尔值。我现在的做法是记录结构化轨迹：每一步的输入上下文（截断后的 token 数）、模型输出的原始 tool_call、工具返回的原始结果、以及耗时。

关键指标不是“步数越少越好”，而是**步数分布**。比如一个检索任务，正常轨迹是 2-4 步（检索 → 重排 → 回答）。如果某条用例走了 11 步，大概率是陷入了“检索不到 → 换 query → 还是检索不到”的循环。我会给轨迹打标签：正常、循环、提前终止、工具报错后放弃。这些标签比 pass/fail 更能指导优化——循环多就加最大步数或查询改写策略，提前终止多就检查系统提示是否让模型过早下结论。

## 错误恢复：区分“能错”和“错了能救”

Agent 一定会调错工具。评估的重点是**第一次工具调用失败后，第二次调用是否修正了参数**。我设计了一个简单的恢复率指标：在注入可控故障（比如让检索工具对某个 query 返回空、让某个 API 返回 500）的用例集上，统计 Agent 在 2 步内切换到正确工具或修正参数的比例。

这里有个反直觉的发现：恢复率高的版本，通过率不一定高。因为有些 Agent 会“过度恢复”——工具报错就换一个完全无关的工具，碰巧蒙对。所以恢复评估必须结合轨迹看：修正后的工具调用是否与原始意图语义一致。我目前用规则 + 小模型打分做这个判断，规则覆盖显式参数错误，小模型判断意图漂移，成本可控。

## 工具调用质量：参数、时机、冗余

工具调用质量可以拆成三个可测维度：

1. **参数正确性**：必填字段是否齐全、枚举值是否合法、数值是否在合理范围。这个可以用 JSON Schema 校验，成本极低，建议每条轨迹都跑。
2. **调用时机**：是否在信息不足时就调用（比如没检索就回答），或在信息充足后还反复调用。我用“必要工具集”做对比：人工标注每条用例最少需要哪些工具，统计实际调用与必要集的差集。
3. **冗余度**：相同工具 + 相同参数的重复调用次数。超过 2 次就标记，通常是模型没读到上一次的结果，或者上下文被截断导致它“忘了”。

## 实现细节与坑

轨迹存储我用 JSONL，每行一条完整轨迹，字段包括 `trace_id`、`steps[]`、`final_answer`、`latency_ms`。评估脚本离线跑，不侵入线上。一个坑是：**上下文截断会改变轨迹**。线上 context window 是 32k，离线评估如果给 128k，模型行为完全不同。所以评估必须用与线上一致的截断策略，包括 system prompt 的 token 预算。

另一个坑是工具返回结果的确定性。检索类工具每次返回可能不同，导致轨迹不可复现。我的做法是评估时固定检索快照（把 top-k 结果落盘），只评估 Agent 的决策逻辑，不评估检索质量——后者单独用 recall@k 评估。

## 还没解决的问题

恢复率目前依赖注入故障，但真实故障分布未知，注入的故障可能不代表线上。另外，轨迹的人工标注成本很高，我在尝试用“同一用例多次采样的轨迹一致性”做无监督信号：如果 5 次采样里 4 次轨迹结构相同，大概率是稳定行为；如果每次都不一样，要么是任务本身模糊，要么是 Agent 不稳定。这个信号目前只用来排序待标注样本，还没敢直接当指标用。

总之，Agent 评估的粒度应该和它的状态机粒度对齐。通过率是给老板看的，轨迹和恢复率才是给自己改代码用的。
