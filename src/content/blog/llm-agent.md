在构建基于LLM的Agent系统时，我们常常陷入一个评估陷阱：只关注最终任务是否成功（pass/fail），而忽略了Agent在执行过程中的行为质量。这种二元评估就像仅凭考试成绩判断学生能力——它无法揭示Agent在复杂环境中的决策逻辑、错误处理能力和工具使用的合理性。本文将从三个维度展开：执行轨迹（traces）、错误恢复（recovery）和工具使用质量（tool-use quality），并讨论如何在实际工程中落地这些评估方法。

## 为什么pass/fail不够？

假设我们有一个客服Agent，任务是根据用户问题查询订单并处理退款。如果只记录最终是否退款成功，我们无法区分：Agent是直接调用了正确的退款接口，还是经过多次错误尝试后偶然成功？后者可能意味着Agent在工具选择上存在严重缺陷，只是被最终结果掩盖了。在真实场景中，这种“侥幸成功”会带来高昂的延迟和资源消耗，甚至引发副作用（如重复调用支付接口）。

因此，我们需要更细粒度的信号。

## 1. 执行轨迹（Traces）：记录Agent的每一步

轨迹是Agent执行过程中所有动作的序列，包括：LLM的输入输出、工具调用参数、工具返回结果、状态变更等。通过分析轨迹，我们可以计算以下指标：

- **步骤效率**：完成任务所需的步骤数 vs 最优步骤数。例如，一个简单的天气查询Agent如果调用了5次工具才得到答案，而最优只需1次，则存在冗余。
- **工具调用分布**：统计每个工具的调用次数和成功率。如果某个工具频繁失败，可能需要检查工具描述或参数格式。
- **上下文长度变化**：记录每步的token数量，避免上下文爆炸。例如，当上下文超过模型窗口的80%时，Agent可能开始丢失早期信息。

实现上，我们可以用OpenTelemetry等标准追踪框架，为每个任务生成一个trace ID，并记录span。以下是一个简化的轨迹记录示例（Python伪代码）：

```python
with tracer.start_span("agent_step") as span:
    span.set_attribute("step", step_idx)
    span.set_attribute("prompt_tokens", len(prompt))
    span.set_attribute("tool_name", tool_name)
    span.set_attribute("tool_args", json.dumps(args))
    result = tool.call(args)
    span.set_attribute("tool_result", result[:100])  # 截断避免过大
```

## 2. 错误恢复（Recovery）：Agent如何应对失败

工具调用可能失败（网络超时、参数错误、权限不足），LLM也可能生成无效的调用。评估Agent的恢复能力，需要关注：

- **重试策略**：是否在失败后重试？重试次数是否合理？是否针对不同错误类型采取不同策略（如参数错误应修正参数，而非简单重试）？
- **回退机制**：当主工具不可用时，是否有备选方案？例如，当数据库查询失败时，是否尝试从缓存读取？
- **错误传播**：Agent是否将错误信息合理整合到后续决策中？例如，工具返回“订单不存在”后，Agent是否停止重试并转向用户澄清？

我们可以设计一个“故障注入”测试集：在工具调用中随机注入超时、错误码等，观察Agent的恢复行为。评估指标包括恢复成功率、平均恢复步骤数、以及是否产生副作用（如重复扣款）。

## 3. 工具使用质量（Tool-use Quality）：不只是调用成功

工具调用成功不代表使用合理。我们需要评估：

- **参数正确性**：调用的参数是否精确？例如，日期格式是否正确，ID是否来自可信来源？
- **工具选择合理性**：在多个可用工具中，是否选择了最合适的？例如，对于“查询天气”，有`get_weather`和`search_web`两个工具，Agent是否优先使用专用工具？
- **调用顺序**：是否存在依赖关系的工具调用顺序错误？例如，先调用`退款`再调用`查询订单`。

为了量化这些，可以构建一个“工具使用评分卡”，对每个工具调用从0到1打分，综合考虑参数正确性、工具选择、顺序等。最终得分可以是轨迹中所有调用的平均值。

## 实施建议

1. **定义清晰的评估维度**：根据业务需求，选择关键指标（如步骤效率、恢复成功率、工具选择准确率）。
2. **构建多样化测试集**：包括正常案例、边缘案例（如模糊用户输入）、故障案例（注入错误）。
3. **自动化评估流水线**：将轨迹收集、指标计算和报告生成集成到CI/CD中，每次模型更新后自动运行。
4. **人工抽样复核**：自动化指标可能遗漏微妙问题，定期人工检查轨迹样本。

## 开放问题

- 如何平衡轨迹记录的详细程度与存储开销？全量记录可能成本高昂，采样策略需要设计。
- 对于多Agent系统，如何跨Agent关联轨迹？分布式追踪需要统一上下文传播。
- 工具使用质量的评分卡权重如何设定？目前多靠经验，缺乏理论指导。

总之，超越pass/fail的评估能让我们更深入理解Agent的行为，从而针对性地改进。下次评估你的Agent时，不妨先问：它真的“聪明”地完成任务了吗？
