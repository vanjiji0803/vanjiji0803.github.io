构建 LLM Agent 时，最让人头疼的不是模型能力不够，而是当它表现异常时，你根本不知道发生了什么。一次用户请求可能触发多轮规划、多次工具调用、若干次检索和重排，最终输出却答非所问。没有可观测性，调试基本靠猜。

## Trace 与 Span：Agent 的调用树

Agent 的一次执行天然是一棵树。根 span 是用户请求，子 span 是规划步骤、LLM 调用、工具执行、检索、重排。每个 span 至少记录：span_id、parent_id、开始/结束时间、类型、输入摘要、输出摘要、状态（成功/失败）、错误信息。

关键设计点：
- **上下文传播**：在异步、并发工具调用中，必须显式传递 trace_id 和 parent_span_id，否则调用树会断。
- **采样策略**：全量记录成本高。可以按错误率、延迟分位数动态采样，但失败请求必须 100% 保留。
- **span 粒度**：太细会爆炸，太粗无法定位。建议以“一次有意义的决策或外部调用”为界。

## Prompt 记录：不只是文本

记录 prompt 时，光存最终字符串不够。你需要知道：模板版本、变量注入后的完整内容、token 数、模型名、温度、top_p、是否流式、以及模型返回的原始响应（包括 tool_calls）。

一个常见坑：prompt 里包含大量检索到的文档，直接存全文会撑爆存储。折中方案是存文档 ID 列表 + 哈希，需要时再回查。但调试时往往需要原文，所以可以设置“调试模式”按需保留。

## 工具输出：结构化与截断

工具输出是失败重灾区。记录时要注意：
- **结构化**：尽量以 JSON 记录，包含工具名、参数、原始返回、解析后的结果、耗时、是否超时。
- **截断**：大输出（如网页全文）只存前 N 字符 + 总长度 + 哈希。
- **错误分类**：网络错误、超时、解析失败、业务逻辑错误要分开，否则无法统计。

## 失败分类法：让问题可度量

没有分类，就无法改进。我常用的一套分类：
1. **规划失败**：任务分解错误、遗漏步骤、循环。
2. **工具选择失败**：选错工具、参数错误、未调用必要工具。
3. **工具执行失败**：外部 API 错误、超时、返回格式变化。
4. **检索失败**：召回不足、无关文档、重排错误。
5. **推理失败**：幻觉、忽略上下文、计算错误。
6. **格式失败**：输出不符合 schema、JSON 解析失败。
7. **安全失败**：越权、注入、敏感信息泄露。

每个失败样本应关联到具体的 span，并打上分类标签。这样你才能回答：过去一周工具选择失败率是否上升？哪个工具最容易超时？

## 实现细节与权衡

- **存储**：初期用 SQLite/Postgres 存 span 和事件即可，量大再上 ClickHouse 或专用 tracing 后端（如 LangSmith、Phoenix、OpenTelemetry）。
- **延迟开销**：异步写入，避免阻塞主流程。采样和截断是控制成本的关键。
- **隐私**：prompt 和工具输出可能含 PII，需脱敏或加密存储，并设置保留期限。

## 评估与迭代

可观测性本身也要评估：trace 完整率、span 丢失率、失败分类覆盖率。可以定期人工标注一批失败样本，检查自动分类的准确率。

我还没试过在超低延迟场景（如手术机器人实时 Agent）中全量记录 span，那需要更激进的采样和边缘缓存策略。这是一个开放的工程问题。

总之，可观测性不是事后补的日志，而是 Agent 架构的一部分。从第一天就设计好 trace、span 和失败分类，后面迭代会轻松很多。
